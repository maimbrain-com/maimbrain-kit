# mb3d — design (v1, Phase 6; v2 at the end)

The host 3D engine: a retained scene graph that games drive through `mb3d_*` calls, rendered by `mb-host` (Rust → wasm32, wgpu on WebGPU) in the same frame as `mb2d`. The flagship that drives it is **Starfall**: a portrait, touch-only, on-rails space shooter through a nebula canyon (sweep to lock on to up to 8 enemies, release for homing lasers; bloom, particles, trails, a crystal boss).

**mb3d 2** (declare `stdlib = { mb3d = 2 }`) adds animated glTF characters (skins, clips, morph targets, bones as nodes), skins built in code (organic meshes animated by bones), instancing, freeing resources, fog, toon shading and outlines, 3D text, depth of field, speed effects (radial blur, motion blur, edge stretch), reflective water (a planar reflector) that reacts (ring ripples and wakes) and looks like water (water v2: a current, a body you see into, foam, glints, caustics), sky v2 (an atmosphere, drifting clouds, a sun or moon disc and painted panoramas over the space sky), and a beauty pass (color grading with LUTs, light shafts, halos around lights in fog, film grain and streaks). See ["mb3d 2"](#mb3d-2) below; everything before it describes v1, which games declaring `mb3d = 1` still get unchanged.

## Decisions

| Area | Decision |
|---|---|
| Look | **Full PBR from the start**: metallic/roughness, image-based lighting, a shadowed sun, emissive glow, HDR, bloom, filmic tonemapping |
| Models | **Built in code and glTF**: raw mesh upload (SDK builders for primitives, lathes, extrusions, flat-shaded low-poly) plus `.glb` loading in v1 (meshopt allowed; PNG/JPEG textures; KTX2 later) |
| Perf floor | **60 fps on iPhone 13 class (A15)**, `perf_tier = "full"`. Effects scale down (particle cap, bloom resolution, render scale) automatically on slower devices |
| Effects | Procedural nebula sky, host particles, ribbon trails, screen effects (shockwaves, chromatic aberration, vignette); camera shake is game-side |
| Determinism | Everything visible comes from guest calls. Particle simulation is host-side, but seeded and stepped only by guest calls and frame dt, so replays reproduce the draw hash exactly |
| Composition | `mb3d_render()` draws the scene; `mb2d` calls in the same `mb_render` draw on top (HUD). A game may use either stdlib alone |

## ABI (import namespace `mb`, stdlib `mb3d = 1`)

Handles are `u32` (0 invalid); fallible calls return `i32` (SPEC §7 codes). Packed structs are little-endian f32/u32, defined in the SDK and SPEC §5.4. Units: meters; right-handed; +y up.

### Resources
```
mb3d_mesh(ptr, len) -> i32                 # packed: header {vertex_count, index_count, flags} + vertices + u32 indices
                                           # vertex: pos f32x3, normal f32x3, uv f32x2 [, tangent f32x4 if flags&1] [, color rgba8 if flags&2]
mb3d_texture(asset) -> i32                 # ready PNG/JPEG asset; sRGB unless used as normal/metal-rough map
mb3d_material(ptr) -> i32                  # Material (below); mb3d_material_set(handle, ptr) updates it (e.g. pulse emissive)
mb3d_gltf(asset) -> i32                    # ready .glb → a model (meshes, materials, textures, node hierarchy)
mb3d_model_spawn(model, parent) -> i32     # instantiates a model's hierarchy under `parent` (0 = root); returns its root node
```
`Material` (64 bytes): `base_color f32x4`, `emissive f32x3`, `emissive_strength f32`, `metallic f32`, `roughness f32`, `base_tex u32`, `normal_tex u32`, `metal_rough_tex u32`, `emissive_tex u32`, `flags u32` (1 unlit, 2 double-sided, 4 alpha-blend, 8 additive), `reserved`.

### Scene graph
```
mb3d_node() -> i32
mb3d_node_parent(node, parent)             # 0 = root
mb3d_node_transform(node, ptr)             # pos f32x3, rotation quat f32x4 (x,y,z,w), scale f32x3
mb3d_node_mesh(node, mesh, material)       # a node draws at most one mesh
mb3d_node_visible(node, visible)
mb3d_node_destroy(node)                    # and its children
mb3d_camera(ptr)                           # pos f32x3, rotation quat f32x4, fov_y (rad), near, far
mb3d_project(x, y, z, out_ptr) -> i32      # world → logical screen xy (+ depth); for 2D HUD over 3D (lock-on reticles)
```

### Lighting and sky
```
mb3d_sun(ptr)                              # direction f32x3, color f32x3, intensity, shadows (0/1), shadow_distance
mb3d_light_point(node, r, g, b, intensity, range) -> i32   # attached to a node; ≤ 8 active
mb3d_sky(ptr)                              # procedural: seed, colors (3 × rgb), nebula density, star density, star brightness,
                                           # sun disc; also the source of image-based lighting (re-baked when it changes)
mb3d_post(ptr)                             # exposure, bloom strength + threshold, vignette, chromatic aberration, saturation, contrast,
                                           # sharpen (was reserved; added with anisotropic filtering)
```

### Effects
```
mb3d_emitter(ptr) -> i32                   # particle look and physics: color over life (4 stops), size over life, lifetime range,
                                           # speed range, spread cone, gravity, drag, blend (additive/alpha), texture (0 = soft dot)
mb3d_emit(emitter, x, y, z, dx, dy, dz, count)   # a burst at a point along a direction
mb3d_emit_moving(emitter, x, y, z, dx, dy, dz, count, vx, vy, vz)  # the same, in a frame moving at v (added after v1 shipped)
mb3d_trail(ptr) -> i32                     # width over age, color over age, lifetime, blend
mb3d_trail_attach(trail, node)             # follows the node's world position; mb3d_trail_detach(trail) leaves it to fade
                                           # attaching to another node (or again after a detach) starts a new ribbon
mb3d_shockwave(x, y, z, radius, strength, seconds)  # screen-space distortion ring at a world point
mb3d_render()                              # draw the scene this frame (mb2d after it draws on top)
```

### Limits (v1)
- **Scene:** 4096 nodes, 512 meshes (1M vertices total), 1024 materials.
- **Textures:** 64 textures, up to 2048² each (96 MB with mipmaps in all). A texture or model refused for texture memory returns −4 and the runtime logs why once per asset, naming the asset, its size and the memory in use; `host_stats` (`mb.stats()`) carries `textureBytes`, `textures`, `textureBudget` and `textureLimit`, and `mb build` sums the bundle's decoded images and glTF images against the budget.
- **Lights:** 8 point lights.
- **Effects:** 16k live particles and 64 trails.
- **Per frame:** 2000 draws.

Going over a limit returns `-4`. GPU memory is capped at 256 MB for `full` games.

In v1 only nodes are ever freed (`mb3d_node_destroy`, with their lights and descendants). Meshes, textures, materials, models, emitters and trails live for the whole session: games build them once and pool them (see "Patterns" below). mb3d 2 adds `mb3d_free`.

## Renderer (mb-host)

- **Targets:** HDR `Rgba16Float` color plus `Depth32Float`, at render scale × (≤ 2× logical). The render scale adapts from frame timings, between 0.6 and 1.0. MSAA 4× where it fits the budget.
- **Forward PBR:**
  - GGX specular, Smith-correlated visibility, Schlick fresnel, Lambert diffuse.
  - Up to 8 point lights plus the sun.
  - The sun casts a 2048² shadow map fitted to `shadow_distance` around the camera, with PCF filtering.
- **Image-based lighting:** the procedural sky is rendered into a 128² cubemap. From that:
  - prefiltered specular mip chain (GGX importance sampling)
  - irradiance (spherical harmonics)
  - a BRDF lookup table baked at init

  Everything is re-baked only when `mb3d_sky` changes.
- **Transparency:** opaque first (front-to-back), then the sky, then alpha and additive (back-to-front), then particles and trails.
- **Post:**
  - bloom (dual-filter down/up chain from a soft threshold)
  - shockwave and chromatic distortion
  - an optional sharpen (`Post::sharpen`)
  - ACES-fitted (or AgX) tonemapping, exposure, contrast and saturation, vignette
  - then `mb2d` composites on top in display space
- **glTF:**
  - `gltf` crate (glb only) and `meshopt` decoding
  - PNG/JPEG textures via the `png` crate and a JPEG decoder
  - node transforms, PBR material mapping and emissive strength
  - skins and animations are ignored in v1

## SDK (`maimbrain::gfx3d`)

- **Math:** `Vec3`, `Quat` and `Mat4`, using `glam` if it stays small.
- **Handles:** `Mesh`, `Material`, `Node`, `Model`, `Emitter`, `Trail`, and setters for the camera, sun, sky and post.
- **Mesh builders:**
  - box, UV sphere, icosphere (smooth or faceted), cylinder, cone, torus, plane
  - lathe (a profile revolved), extrude (a 2D polygon along z)
  - `flat_shaded()` for low-poly facets, `with_vertex_colors`
  - merge, transform
- **Helpers:** an orbit/follow camera and `look_at`.

## Spec, validator, runtime

- **SPEC §5.4:** rewritten to this API.
- **mb-format:** ABI table entries, gated by `stdlib = { mb3d = 1 }`; `.glb` size checks.
- **runtime:** `abi.ts` marshals the memory-passing calls into mb-host's scratch buffer, as mb2d does.
- **Skill:** a "3D" section with performance budgets, how to make meshes in code, how to build a glTF with a script, and lighting recipes.

## Implementation notes (v1, as built)

The API above is what shipped; SPEC §5.4 is the normative version with every struct layout. Where the build differs from this design, deliberately:

- **glTF without the `gltf` and `meshopt` crates.** mb-host reads `.glb` with its own small JSON reader and glTF walker, and decodes meshopt with a safe Rust port of meshoptimizer's reference decoder (tested against vectors from its encoder). The `gltf` crate pulls serde/serde_json, and the `meshopt` crate is a C build that doesn't fit the wasm32 toolchain. Besides `EXT_meshopt_compression`, the loader takes `KHR_meshopt_compression` (vertex codec v1, color filter), which current gltfpack can emit.
- **Small ABI decisions** the design left open: `mb3d_material_set` returns `i32` (0 or −1); `mb3d_light_point` returns 0 or a §7 code (lights are addressed by their node, so there's no light handle); `mb3d_project` returns 1 when the point is on screen and writes the view depth; the sun's `direction` is the way light travels; `Emitter` has a `gravity` vector and a velocity `stretch`, `Trail` a `min_segment`; `Sky` is 64 bytes with two reserved words.
- **Limits added**: 256 emitters, 64 models, and a 96 MB texture budget (64 textures at 2048² with mips would be 1.4 GB, far over the 256 MB cap).
- **Scaling on slow devices is resolution only.** The render scale adapts (0.6–1.0) from frame timings; the particle cap does not, because particle counts are simulated state and must replay identically on every device. MSAA is always 4×.
- **Determinism plumbing**: the runtime calls a new `host_step(dt)` before each `mb_update` so effects advance by the recorded `dt` even on frames that don't render; `host_frame_time(ms)` feeds the adaptive render scale. Every mb3d call, plus a digest of particles, trails and shockwaves at each `mb3d_render`, is folded into the draw hash.
- **Bakes without compute**: the nebula cube (every mip rendered directly), the GGX-prefiltered specular cube, the SH coefficients (a 9×1 render target the PBR shader reads) and the BRDF table are all render passes, so nothing needs compute or storage textures, and nothing is read back. A sky change is compared by value and re-baked over six frames (the sky draws stars only until its nebula is ready).
- **Tonemapping is ACES-fitted** (AgX not added). No fog in v1. glTF alpha `MASK` draws opaque.
- **Assets**: `.jpg`/`.jpeg` are now allowed in bundles (SPEC §1) for `mb3d_texture`; `.glb` assets are structure-checked by the validator and capped at 8 MB.

### Changes after Starfall (the clean-room build)

- **`mb3d_emit_moving`**: particles had no base velocity, so a burst on an enemy flying alongside the camera streamed away behind it. A burst can now carry its frame's velocity: each particle keeps it unchanged and moves by `vel + base`, with gravity and drag acting on `vel` only (so the cloud keeps pace and spreads as it would at rest). The emitter's burst counter is shared with `mb3d_emit`; `base` isn't in the particle digest because it only shows through positions, which are. ABI table, validator, SDK (`Emitter::emit_moving`), SPEC §5.4 and tests (`a_moving_burst_drifts_with_its_frame`).
- **Trail re-attach**: re-attaching used to clear the trail's points at once (a fading ribbon popped out of existence when a pooled trail moved to a new node). Now the old points stay and fade on their own clock, and the new ribbon starts at the node's next sample, with nothing drawn between them (the strip joins ribbons with degenerate triangles; the ribbon buffer is 3 × points per trail to fit the joins). Attaching to the node already followed is a no-op.
- **Projection** is specified exactly in SPEC §5.4, and the SDK's `Camera::project` computes it in plain Rust (tested against the host formula), so lock-on and hit tests can live in a game's tested simulation.
- **Draw hash per session**: `host_new_session` restarts the hash, and the runtime counts frames per session, so a run and its replay (or two runs) can be compared at equal frame counts; see SPEC §9 for the procedure (`mb.restart({hold})`, `mb.step`, `mb.verify`).

## Patterns

- **Explosions on things that move with the camera.** Particles are world-space. For an on-rails game where the camera (and the enemies around it) fly forward at the rail speed, fire bursts with `Emitter::emit_moving(pos, dir, count, velocity_of_the_thing)` so the cloud rides along. The alternative is a floating frame: keep the player and camera near the origin and move the world past them (scenery scrolls backward); then bursts on things flying with the camera need no velocity, and bursts on scenery need the scenery's (backward) velocity. Pick one frame for the whole game; mixing them is where streaks come from. Long-lived effects on curved paths will drift (the frame velocity is constant per burst), so keep those short.
- **Build once, pool.** Create meshes, materials, emitters and trails in `init` (or when an asset arrives) and keep the handles. One emitter per particle *look*, fired wherever needed; one material per look, changed with `Material::set`; enemies as a fixed pool of nodes, hidden with `set_visible(false)` when dead and moved when reused. Pooled trails move with `detach()`/`attach(node)`, which starts a fresh ribbon.
- **Lights.** A point light holds one of the 8 slots from its first `mb3d_light_point` until its node (or an ancestor) is destroyed. Intensity 0 darkens it but keeps the slot; hiding its node doesn't turn it off. For explosion flashes, keep one or two light nodes, move them to the latest blast and decay their intensity.

## mb3d 2

Closes the gaps between mb3d 1 and what three.js + drei give AI-built web games (animated glTF characters, instancing, disposing resources, fog, toon/outline looks, 3D text, depth of field), without changing anything for games that don't ask for it. The showcase is **Mistwood** (`games/mistwood`): a toon fox with a lantern on its tail runs a foggy, instanced forest; tap to jump the logs.

### Decisions

| Area | Decision |
|---|---|
| Versioning | `stdlib = { mb3d = 2 }`. A stdlib version only adds imports: the host serves 1–2, a v2 import needs `mb3d = 2`, and a game declaring `mb3d = 1` validates, links and renders exactly as before (checked: old bundles and their rebuilt-from-source versions replay to the same draw hashes and pixels) |
| Animation | **The game owns time.** `mb3d_anim(node, clip, time, weight)` adds one weighted sample of a clip, at a time the game passes, to a spawned model's pose for this frame; the host blends and resolves when it next needs world transforms. Nothing advances on its own, so replays pose identically. The SDK's `Animator` (pure Rust) does play/loop/once, speed and crossfades on top |
| Bones | Bones and sockets are ordinary nodes of the spawned model, found by glTF name (`mb3d_node_find`). Attaching a sword to a hand is parenting; `mb3d_node_world` reads where a bone is |
| Skinning | GPU, 4 weights per vertex, ≤ 64 joints per skin (a 4 KB uniform palette per skinned draw), ≤ 128 skinned draws per frame. Morph targets: the first 4 of a glTF mesh, positions and normals, blended in the same vertex shader |
| Instancing | A node with an instance list draws its mesh once per instance in one draw call (`pos, rot, scale, rgba8` = 44 bytes each), culled as one sphere. Lists are uploaded only when they change |
| Freeing | Generational handles for meshes, materials, textures, emitters, trails and models (`mb3d_free(kind, handle)`): stale handles never reach a reused slot, and handles stay 1, 2, 3, … until something is freed, as v1 promised |
| Looks | Fog (linear, exponential, exp², optional height falloff, sky fade), per-material styles (cel bands, rim light, inverted-hull outline with smoothed normals, no-fog flag), 3D text from the host fonts (SDF Inter with outline, or the pixel font; world-space or billboard, optionally a fixed screen size), half-resolution gather depth of field, one planar reflector for water and polished floors (see [Reflections](#reflections-mb3d_reflector-added-after-the-speed-effects)) and a look for its water (see [Water v2](#water-v2-mb3d_water-added-after-the-organic-meshes)), sky v2 layers over the space sky (see [Sky v2](#sky-v2-added-after-the-reflections)) |
| Compatibility | mb3d 1's fragment shaders (`fs`, `fs_sky`, `fs_particle`, `fs_trail`) are kept verbatim and used unless a material or the scene opts into a v2 look; v2 pipelines are built lazily the first time they're needed |

### Animation, as built

- **glTF:** `skins` (joints must be nodes of the default scene; a skin over 64 joints is dropped and its meshes draw unskinned), `JOINTS_0` (u8/u16) and `WEIGHTS_0` (float or normalized; renormalized to sum to exactly 1 in unorm16), morph `targets` (first 4; POSITION and NORMAL deltas) and `weights`, `animations` (translation, rotation, scale and weights channels; `STEP`, `LINEAR` (rotations slerp) and `CUBICSPLINE`), node `name`s. Channels on nodes outside the default scene or with malformed samplers are skipped; a clip's duration is its last key time.
- **Pose:** per node, samples accumulate per path (rotations hemisphere-aligned). Weights short of 1 are filled with the node's rest pose (its glTF TRS), weights over 1 are normalized; paths no sample touched keep the node's current value, so a game can still drive other nodes by hand. Samples are dropped at the start of each frame (the pose they made stays), so a frame without `mb3d_anim` calls holds the last pose.
- **Skinning:** palettes are world-space (`world(joint) × inverseBind`); the skinned mesh node's own transform is ignored, as glTF says. A skinned draw is culled by a sphere around its joints, each grown by how far its vertices reach at bind time. Morph-only meshes use a one-matrix palette (the node's world).
- **Cost:** 8 foxes × 2 clip samples = 6 µs per frame, natively (`cargo test -p mb-host --release perf_report -- --ignored --nocapture`); wasm is roughly 1.5–2× that.

### Instancing, freeing, looks, as built

- **Instances** multiply the material's base color, alpha *and* emissive by their color (glowing mushrooms in three tints from one material). Instanced draws always use the v2 fragment shader. Transparent instances aren't sorted among themselves. Split big fields into chunks so culling has something to cull (Mistwood: 7 chunks of 16 m, trees/grass/mushrooms per chunk, re-laid out only when a chunk leapfrogs ahead).
- **Freeing** a mesh leaves nodes that use it drawing nothing; a material, drawing with the default; a texture, sampling white (materials that used it rebuild); an emitter, its live particles finish their lives and its slot comes back after; a trail, its ribbon vanishes; a model, its meshes, materials and textures go with it. Freed resources stop counting against the limits.
- **Fog** applies to lit and unlit surfaces, outlines, 3D text, particles and trails (additive ones fade out, alpha ones fade to the fog color) and, by `sky`, the sky toward the horizon. Height fog integrates `density × e^(−falloff (y − height))` along the view ray (clamped so it can't overflow).
- **Outlines** are inverted hulls drawn right after the opaque pass: back faces pushed out along per-mesh smoothed normals (computed once, the first time a mesh draws outlined) by a fixed width in logical pixels. Opaque materials only.
- **Toon** quantizes the sun's and point lights' N·L into `toon_bands` with soft edges, a hard-edged highlight, flat sky ambient and half-strength reflections. **Rim** adds a sun-colored edge.
- **Text** is laid out once per change on the CPU (in em units around the alignment anchor) and drawn from the host font atlas; changing only its color or size keeps the layout and GPU buffer, so fading a pop every frame is cheap. Text draws are sorted with transparent things.
- **Depth of field** keeps the main pass's MSAA depth (it's normally discarded) and makes two half-resolution passes: CoC from the nearest of each 2×2 depth block, then a 24-tap golden-spiral gather where background blur can't bleed over sharper foreground but foreground blur spreads. The composite blends by the blurred CoC. Bloom reads the unblurred scene.

### Limits and budgets

| | Limit (−4 past it) | Budget for 60 fps on A15 |
|---|---|---|
| Instances | 16 384 per node, 65 536 in all | count instances × triangles toward the 150 k triangle budget; each instanced node is one draw (two with an outline, one more per shadow pass) |
| Skins | 64 joints per skin; 128 skinned draws per frame (more are skipped) | a handful of characters; each skinned draw uploads a 4 KB palette |
| Morph targets | first 4 per mesh | — |
| 3D text | 256 nodes, 512 characters each, 16 384 glyphs in all | each text node is one draw |
| Outlines | 0–8 logical px | each outlined draw draws again (vertex cost × 2); keep to characters, props and big shapes |
| Depth of field | blur 0–16 logical px | ~0.3–0.6 ms GPU estimated (below); turn off when not needed |
| Fog, toon, rim | — | a few ALU per pixel |
| Ripples and wakes | 16 rings (the oldest gives way), 4 wakes of 12 path points | a few dozen ALU per ring and ~150 per nearby wake, only on reflective pixels the ring or wake reaches: +0.3–0.5 ms GPU for the canal's koi in headless Chrome (below), nothing while the water is calm |
| Water v2 | one look at a time | per water pixel 4 texture reads (~10 more with `depth_fade` or `foam`) and a loop over the lights; with `depth_fade` or `foam`, a second view of what reaches below the plane at the reflection's resolution (`under` draws): +0.2–0.5 ms GPU for the canal, +0.9 ms over a plain mirror for the koi pond on an M-series Mac (below) |
| Beauty pass | grade, shafts, halos (≤ 8 point lights), film; LUT N²×N with N 2–64 | the whole pass +0.53 ms on the canal (M-series, headless Chrome), ~2 ms estimated on an A15; most of it shafts and streaks (see [The beauty pass](#the-beauty-pass-mb3d_grade-mb3d_shafts-mb3d_halos-mb3d_film-added-after-the-organic-meshes)) |
| Reflector | one at a time; resolution 0.25–1 of the scene's | a second pass over what's above the plane (+1 draw per reflected mesh, at ¼ the pixels by default): +0.15 ms GPU measured on an M1 Pro, ~0.6–1 ms estimated on an A15 (below); 0 while no reflective surface is on screen |

### Performance (measured in the desktop preview, reasoned for A15)

CPU, desktop Chrome on an M-series Mac, `mb.stats()` over 120 live frames of Mistwood (57 draws, 34.8 k triangles, 2 299 instances, 1 skinned draw, 21 outlines, 31 shadow casters, DOF on): `mb_update` 0.06 ms, `mb_render` 0.01 ms, presenting (the host's draw collection, uploads and WebGPU encoding) 0.32 ms average, 1.1 ms worst. WebKit on an A15 is perhaps 3–4× slower at this: ~1–1.5 ms, well inside the frame. Natively: re-sending 16 384 instances costs 97 µs (do it only for lists that move, like Mistwood's coins), a 14-character text relayout 0.7 µs, parsing the 866-vertex fox with four clips 0.7 ms (once, at load).

GPU (no timestamp queries in WebGPU by default, so estimated): Mistwood's main pass is ~35 k triangles plus ~25 k for outlines and ~30 shadow draws at 720×1280 with 4× MSAA, which the A15's tile memory resolves cheaply. Depth of field adds the MSAA depth store (720×1280×4 samples×4 B ≈ 15 MB per frame, ~0.9 GB/s at 60 fps, a few percent of the A15's bandwidth) and two half-res passes (230 k pixels; ~29 texture reads each in the gather), roughly 0.3–0.6 ms. Skinning (866 vertices × 4 joints) and fog are negligible. All of this needs a real A15 to confirm (below).

### Speed effects (`mb3d_speed`, added after Mistwood)

Racers and chases need speed to *feel* fast, which the post chain couldn't do. `mb3d_speed(SpeedBlur)` adds three effects to the final composite pass, so they need no extra render targets and cost nothing while off:

- **Radial blur**: 10 jittered taps toward `center`, the reach growing with distance from it (none within ~4% of the screen). Put `center` on what the camera chases (project it with `Camera::project`): the world streaks outward from it, which reads as forward motion blur.
- **Motion blur**: the same taps spread along `motion` (logical pixels, clamped to 48): the game passes how far a far point moved on screen since the last frame, so bends and camera swings smear sideways.
- **Edge stretch**: the left and right edges sample from nearer the middle (`stretch` 0–1), a wide-lens rush at the borders.

Chromatic aberration is applied on top of the blurred scene, so fringes stay crisp. The call is part of the draw hash like every other.

### Reflections (`mb3d_reflector`, added after the speed effects)

A night runner down lantern-lit canals was unreadable: near-black water reflecting a dark sky cubemap (at 128², so a smooth surface showed blocky stars), with nothing on it to say where the course was. Water that mirrors the lanterns, the torii and the moon, rippling, is what makes that kind of scene read. The vignette is the **moonlit canal** in `games/mb3d-demo` (tap CANAL; tap again to compare: water v2 from low by the wall, the reflector alone (water v1), fog only, neither).

- **API.** `mb3d_reflector(Reflector)` sets one horizontal mirror plane at `height`; materials with the new flag **16, reflective** show it. `strength` 0 (the zeroed struct) is off; the last call wins, so there is one reflector at a time. Other fields: `resolution` of the reflection (0.25–1 of the scene's, 0 = 0.5), `blur`, `max_distance` (nothing farther from the camera is reflected), and the ripples: `ripple_tex` (a tiling normal map, or 0 for procedural waves), `ripple_scale` (meters per tile), `ripple_speed` (m/s drift), `ripple` (how far they tilt the surface) and `distortion` (how far they shift the reflection). `MaterialStyle` flag 2 keeps a material out of the reflection. An mb3d 1 game's material flags are still masked to 1–8. SDK: `gfx3d::reflector(&Reflector::water(y))` (or `Reflector::mirror(y)`), `Material::REFLECTIVE`, `MaterialStyle::NO_REFLECTION`.
- **The pass.** Before the main pass the host draws the scene from the camera mirrored in the plane (`view_proj × reflect(y = h)`) into an HDR target at `resolution` × the scene's size (which already follows the adaptive render scale), single-sampled, then builds a ≤ 5-level mip chain from it. Mirroring flips winding, so its pipelines treat clockwise triangles as front faces; `fs_mirror` shades exactly as `fs_styled` does (PBR or toon, rim, instance tints, fog) and discards whatever is below the plane. The draw list (`Scene::collect_reflected`) is meshes, skinned meshes and instanced nodes at least partly above the plane, inside the mirrored frustum and within `max_distance`, minus reflective materials and `NO_REFLECTION` ones; opaque front to back, then the sky, then transparent ones back to front. Not reflected: shadows (the reflection is lit without the sun's shadow map), outlines, 3D text, particles, trails, shockwaves.
- **Skipping work.** The pass runs only when the reflector is on *and* a reflective material is among the frame's drawn meshes, and it is scissored to the screen rectangle those surfaces cover (their bounding spheres, projected), widened by what ripples and blur can reach. A canal filling the lower half of the screen renders about half the reflection target.
- **Shading.** A reflective material looks its reflection up in screen space, at its own pixel, offset by the ripple slope (scaled by `distortion`, shrinking with distance) and at a mip given by `blur` plus its roughness. The reflection stands in for the sky's prefiltered specular (`pre = mix(pre, reflection, strength)`), so it's weighted by the same split-sum Fresnel: smooth water mirrors strongly at grazing angles and faintly straight down, a metal everywhere, toon materials at half strength like their sky reflections. The ripples also tilt the normal for the sun's and point lights' highlights (lanterns glint on the water). Procedural ripples are five directional waves with dispersion, each faded out before it gets finer than a couple of pixels; a `ripple_tex` is sampled twice at different scales drifting two ways. Unlit reflective materials add the reflection to their color.
- **Composing with the rest of mb3d 2.** *Fog*: the water pixel is fogged from the camera to the water as usual, and the reflection pass fogs each reflected point from where the reflected ray leaves the water (`fog_origin`), so a reflected lantern is fogged over the whole path camera → water → lantern, like the real one at that distance; the reflected sky fades toward the horizon the same way (`fs_sky_fog`). *Depth of field* reads the main pass's depth, so a reflection blurs as the water surface does (a real lens focuses a reflection at its mirror distance; at phone DOF strengths the difference doesn't show). *Bloom, speed blur, shockwaves, chromatic aberration, exposure* apply to the final image, reflections included. *Outlines* aren't reflected (the outlined thing is, without its outline). *Instancing, skinning, morphs* reflect (checked with Mistwood's fox, instanced trees and grass on a temporarily reflective ground).
- **Determinism.** The pass is host-side rendering only. `mb3d_reflector` is folded into the draw hash like every other call (op 0x100 + 42); `mb.verify()` matched over 380 frames of the canal, switching the reflector on and off.

Measured in the desktop preview (Chrome, M1 Pro, the canal at 720×1280 with 4× MSAA, ~28 reflected draws, ~4 k triangles each way), using WebGPU timestamp queries around every pass (a temporary page hook, not shipped). Per-pass timestamps overlap on a tile GPU, so the cost is the frame's GPU span: fog only 0.92 ms, with reflections 1.05–1.11 ms, so **+0.13–0.19 ms GPU** (the reflection pass itself ~0.13 ms; the main pass +0.1 ms for the water's ripples and lookups). CPU, `mb.stats()` presenting: 0.07 ms → 0.13–0.15 ms (the second draw list and its encoding). An A15 has about a quarter of the M1 Pro's GPU throughput and a sixth of its bandwidth: roughly **0.6–1 ms** there for this scene, inside the 16.7 ms frame with the rest of the canal; to confirm on a device. Budget a reflected draw like any other draw: the canal at 29 draws + 28 reflected stays far inside ≤ 200 draws and 150 k triangles. To make it cheaper: `resolution` 0.25–0.35 (a ripple hides it), `max_distance` at about where the fog hides things, `NO_REFLECTION` on things the water can't show.

Not done: more than one reflector (the target and the frame uniform hold one plane; a second plane would be a second pass); reflections on tilted or curved surfaces (the plane is horizontal and screen-space lookups assume the surface lies in it); and clip-distance clipping, which WebGPU doesn't guarantee (the pass discards below the plane instead, which keeps tile GPUs' hidden-surface removal off in that small pass only).

### Sky v2 (added after the reflections)

A player testing a moonlit night runner (a koi in lantern-lit canals, using fog and the reflector) asked for "more beauty in the skybox", and said the environment felt empty. mb3d's only sky was Starfall's: a space background with a seeded nebula, stars and a sun disc, baked into the cube that also lights the scene. It can't do an atmosphere, a glow at the horizon, clouds or a moon with a halo, or show a painted sky. Sky v2 adds those as layers over it, each its own mb3d 2 call with a struct whose zeroed form is off, so games that don't call them (mb3d 1 or 2) keep their sky exactly. The vignette is the moonlit canal in `games/mb3d-demo`: tap the bottom of the screen to switch between its night, dusk and painted skies and mb3d 1's.

- **Atmosphere** (`mb3d_atmosphere(Atmosphere)`): a gradient from `zenith` to `horizon` (reaching up to `horizon_height`, the sine of the elevation where the sky is ~⅔ zenith-colored) and quickly to `ground` below the horizon; a glow `band` along the horizon (`band_height`; `band_sharpness` from an exponential tail to a flat-topped band with a crisp edge, thinner below the horizon); and a `glow`, a halo of radius `glow_size` around the sky's light (toward the sun, `−Sun.direction`): a Gaussian core plus a long Lorentzian-like tail, enough for a sunset's glare or a moon's corona. The gradient replaces the `Sky`'s background color; a `Sky` nebula still draws over it, thinning toward the horizon (the atmosphere's haze), and the stars fade out near the horizon and over anything bright behind them (the band, the halo, a day sky): `exp(−30 · max(luma − 0.015, 0))`, by the atmosphere's own brightness so a bright nebula doesn't hide them. SDK: `gfx3d::atmosphere(&Atmosphere::night())`, `::dusk()`, `::day()`.
- **Clouds** (`mb3d_clouds(Clouds)`): one layer of soft 2D clouds, not volumes. A sky direction `d` maps to a point on a plane over the camera bent down to meet the horizon ~12 units away (`d.xz / (max(d.y, 0) + 0.08)`, scaled by `5 / size`), drifting by `speed × direction × time` with the scene's simulation time (the sum of frame `dt`s), so clouds replay exactly and pause with the game. Density is a threshold (from `coverage`, softened by `softness`) of two layers of a tiling fBm noise texture: a broad one, and a finer one at 3.8× that drifts 60% faster, so clouds change shape as they move. Lighting: a second lookup a little toward the light along the layer says whether this side faces it (`color`) or away (`shade`), thick parts are darker, and thin edges glow toward the light (a forward-scattering lobe, `silver`) — the silver lining around the moon. Clouds fade into the sky toward the horizon and are composited over the stars and the sun disc, before fog. The noise is a 256² RGBA8 texture with mips (two independent five-octave value-noise fBm layers, wrapping), made on the CPU once, the first time a game shows clouds (`mb3d::sky::cloud_noise`); it's bound to the frame bind group (binding 11; 1×1 black until then). Sampling with mips keeps far clouds from shimmering near the horizon.
- **Sun or moon disc** (`mb3d_sky_disc(SkyDisc)`): replaces the `Sky`'s `sun_disc` (a flat disc with a glow) with a sphere seen from afar, all procedural: within `radius` (angular) of its direction, a point on the disc is `q` in the unit circle and `μ = √(1 − |q|²)` the cosine toward the viewer on the sphere; brightness is `color × (1 − limb · (1 − μ^0.7))`, times dark seas where a 4-octave value-noise fBm over `(q, μ)` passes a threshold (`maria`, placed by `seed`) and a fine grain. The edge is anti-aliased over a pixel, the disc hides the stars behind it, the clouds pass in front of it, and a `halo` falls off exponentially over `halo_size` past the edge (the atmosphere's `glow` is the broad halo, this one the tight corona). Its direction (zero = toward the sun) is the sky's light for the halo and cloud lighting, so a moon placed away from the scene's light still has its corona and silver linings around it. Leaving it zero keeps everything consistent: the disc, the sun's specular highlight on water and the halo coincide, and the reflector shows the disc mirrored where the highlight is (its pass draws `fs_sky2` with the mirrored camera). The disc isn't part of the lighting bake (as `sun_disc` wasn't): the sun is the light. Keep a moon's `color` near 1–1.5: far above that tonemapping turns it flat white and the seas disappear (bloom then comes from the halo).
- **Painted sky** (`mb3d_sky_texture(texture, SkyTexture)`): an equirectangular panorama (2:1; a bundled PNG or JPEG through `mb3d_texture`, so the usual limits: ≤ 2048², 64 textures, 96 MB) as the background. Direction `d` maps to `u = atan2(d.x, −d.z)/2π + ½ + yaw/2π` (the middle column straight ahead, −z; turning right moves right across the image) and `v = acos(d.y)/π` (top row straight up). It's baked into the sky cube by `fs_nebula2`, so it costs nothing per frame and lights the scene (the specular cube and SH come from the cube as always). The bake samples it with a sampler that repeats in u and clamps in v, so bilinear filtering wraps across the left/right seam, and at an explicit level of detail (derivatives jump at the seam): the mip whose texel matches a cube texel at that cube level, widened toward the poles by `½ log2(1/cos φ)` (the geometric mean of the stretched row and the column there), so the pinched rows near the poles are averaged rather than aliased. A 2048-wide painting matches the 512² cube's mip 0 (both ~326 texels per radian). `procedural` mixes the procedural sky (gradient, nebula) over all of it; `fade` (a sine of elevation) hands over to the procedural sky above that height over ~15°, for a painted horizon under a procedural sky. Stars show over the painting's dark parts, above ~10° (a painted skyline doesn't get stars); clouds, the disc and the halo draw over it. A handle that isn't a live texture returns −1 and removes the painting; a texture that fails to decode or is freed later leaves no painting (the bake key holds the handle, generation-checked). Decoding a 2048×1024 JPEG makes one long frame when the texture is created (on an M1 Pro, one 33 ms frame instead of 17), so create it behind a scene change or a loading moment; the canal creates its painting's texture when the painted sky is first chosen, not when the canal opens. `mb art sky` makes paintings in this projection from an image model, with the seam joined and the poles calmed (GENERATE.md "Skies"); the canal's painted sky (`assets/sky_night.jpg`) is one, from Nano Banana 2.1 for $0.05.
- **Drawing and baking.** The gradient and band don't move, so they're baked into the sky cube with the nebula (`fs_nebula2`, instead of `fs_nebula`, when the gradient is on) and the background draw samples the cube as before. The halo follows the sun, which a game may move every frame, so `fs_sky2` draws it per pixel (with the stars, the sun disc and fog); a v2 cube keeps in its alpha the brightness the stars fade over (the gradient's or the painting's, not the nebula's), so the gradient isn't worked out again per pixel, and the halo and the disc measure angles by their chord (`sky_angle`) rather than `acos`; `fs_sky` and `fs_sky_fog` are untouched and still draw every sky without v2 layers. The reflector's pass draws the same `fs_sky2`, so the water mirrors the gradient and the halo.
- **Lighting.** The specular cube and the SH are baked from the cube plus what `fs_sky2` draws over it (`lit_sky` in `sky.wgsl`, skipped entirely without sky v2, so mb3d 1 lighting is bit-for-bit what it was): the halo, and the clouds as an even haze of their average color over the fraction of the sky they cover (`clouds_mean`). Changing the gradient or band re-bakes everything (six frames, as for `mb3d_sky`). The halo's direction in the bake is held until the light has moved ~2° (`Gpu3d::sky_key`): then only the specular cube and SH are re-baked (two frames), and the cube is kept; changing the clouds' look does the same. A sun crossing the sky (180°) in a minute re-bakes them about every 0.7 s; without a halo, moving the sun never re-bakes, and drifting clouds never re-bake anything. Rough and metal surfaces reflect the haze; the planar reflector shows the real clouds, since its pass draws `fs_sky2` too.
- **Compatibility.** `Sky` and `mb3d_sky` are unchanged. The frame uniform and the bake uniform grew (`SkyV2`, 16 × vec4; bake slots are now 512 bytes) and the frame bind group has the cloud noise at binding 11, none of, which v1 shaders read. Checked: Starfall (mb3d 1), Mistwood and mb3d-demo's first scene (mb3d 2, no sky v2) give pixel-identical screenshots on the old and new host. Sky v2 calls are folded into the draw hash like every other (ops 0x100 + 43 atmosphere, + 44 clouds, + 45 sky disc, + 46 painted sky, with its texture handle and result); `mb.verify()` matches over the canal's night, dusk and space skies.
- **Cost.** Measured in the desktop preview (Chrome, M1 Pro; the canal at 720×1280 with 4× MSAA, sky over ~45% of the screen, plus its reflection) with `mb measure` (GPU time over 60 paced steps, three runs each), by making a sky shader run 17 times per pixel and dividing the extra time, everything else unchanged: mb3d 1's sky (`fs_sky_fog`, the canal has fog) costs **0.31 ms** a frame there (3.2 → 8.1 ms at 17×), nearly all of it the hashed starfield. With sky v2 (`fs_sky2`, 17×: night 10.5, dusk 9.1, painted 7.8 ms): the night sky (gradient, halo, stars, clouds, moon, fog) **0.45 ms**, dusk 0.37 ms, the painted sky 0.29 ms (fewer stars over it). The clouds are the one real addition: **~0.12 ms**, also measured alone by evaluating them 33 times (3.0 → 6.8 ms): four texture samples and a few dozen ALU per sky pixel, nothing without clouds. The gradient, band and painting are baked, so they're free per frame; the halo and the disc are a few ALU (the disc's noise runs only on its own pixels). A whole canal frame stays at 3–4 ms GPU (p50) with any of the skies. An A15 has about a quarter of the M1 Pro's GPU throughput: ~1.8 ms for the night sky over half the screen, ~0.5 ms of it clouds and ~0.6 ms more than mb3d 1's sky, to confirm on a device. Spending less: fewer or no stars (`star_density`, the biggest part), clouds off, or more of the screen covered by the scene (the sky draws only where nothing opaque did).

### Water that reacts (`mb3d_ripple`, `mb3d_wake`, added after reflections)

A player trying a koi runner on the canal asked for "more physics around the water": the ripples were ambient only, and nothing answered the koi. Now the game can disturb the reflector's water: rings where things land, surface or drop in, and wakes behind things that move. The canal shows both (below).

- **API.** `mb3d_ripple(x, z, strength, speed, seconds)` starts a ring at (x, z) on the reflector's plane: a packet of about three crests whose front leaves at `speed` m/s, crests `speed` × 0.35 s apart, `strength` 0–1 how steep they start (1 is a slope of 0.45, ~24°), gone after `seconds`. `mb3d_wake(wake, x, z, vx, vz, size, strength)` places wake 0–3's source this frame: where it is, its velocity, its size across and how hard it churns (0 stops it; what it made fades). SDK: `gfx3d::ripple(at, strength, speed, seconds)`, `gfx3d::wake(index, pos, velocity, size, strength)`, and `Ring` (a ring as a value: `start()`, and `height(p, age)`, the same wave in plain Rust, for floating things to bob on).
- **Rings.** The shader adds, per ring, `slope × packet(u) × cos φ` along the ring's radius, where `u = (radius − d) / λ` is how many wavelengths a point is behind the front, `packet(u) = e^(−(u − 1.1)² / 0.72)` (three crests just behind the front, none past −0.6 or 3.2), and `φ = 2π(u + radius / λ)`, so crests run through the packet at twice its speed as on deep water: born at its back, gone at its front. The slope fades in over 0.06 s, out as `(1 − age / seconds)²`, and as `1 / √(1 + radius / 3λ)` as the ring spreads. Waves finer than a couple of pixels fade out (as the ambient ones do).
- **Wakes.** The host keeps each source's path: its position every 0.2 s of simulation time, 12 points (~2.2 s) including where it is now, with its speed and strength then. Per pixel the shader finds the nearest point on that path (11 segments, skipped outright outside the wake's bounding circle) and from there evaluates, in the path's own frame:
  - **divergent waves**: the same packet, crests parallel to the track, at an arm radius `size / 2 + 0.354 · v · τ` (τ: how long ago the source passed; 0.354 is tan 19.47°, the Kelvin wedge's half-angle), so the arms open into a V behind the source and keep spreading after it has gone; wavelength `1.4 × size`. Around the source itself, where the nearest path point is the source, the packet wraps its front: the bow wave, a little stronger straight ahead.
  - **transverse waves** inside the V, across the track, with deep water's wavelength 2πv²/g (capped at 3 × size + 0.2 m for small fast things), moving with the source.
  - **churned foam** along the track, `size / 2` wide at the source and widening with the arms, in patches, fading over ~0.7 s.

  Their slope grows with speed (`v / (v + 1)`), fades with age (`(1 − τ / 2.2 s)²`) and as the arms spread. A source that moves more than 2 m between calls starts a new path (a pooled boat reused elsewhere doesn't draw a wake across the canal).
- **Shading.** (With a water v2 look, below, their foam also breaks into patches carried by the current, in the look's `foam_color`.) Rings and wakes add their slope to the ambient ripples' (after `ripple` scales those), clamped to 1, so they tilt the lights' highlights and shift the reflection by the reflector's `distortion` just as the ambient ripples do. **Foam** comes from steep crests (`smoothstep(0.12, 0.36, crest height as slope)`) and from wakes' tracks: it turns the surface pale (albedo toward 0.6) and rough (toward 0.7), and since foam scatters rather than mirrors, it adds `0.6 × sun` (whatever the sun's angle) and the reflection's second-blurriest level (what the water would have mirrored, so foam under a lantern glows warm). Unlit reflective materials get a dimmer version. Only reflective materials with the reflector on show any of it; the reflection pass doesn't run the wave code (reflective materials aren't reflected), and its scissor widens by the extra tilt while waves are alive.
- **Determinism.** Rings age by the recorded `dt` in `host_step`; wake paths are sampled on simulation time; both calls are in the draw hash (ops 0x100 + 47 and + 48, with their arguments), and once a game has used either, `mb3d_render` also folds a digest of the rings and wake paths. Games that never call them hash exactly as before. `mb.verify()` matches over 780 frames of the canal (leaps, splashes, rising fish, the wake switching on and off).
- **Splashes** are SDK particles (`EmitterDesc::water_crown`, `water_droplets`, `water_mist`, `water_spray`, and `Splash`, which fires them with two rings); see the skill's "Water that reacts".

**The canal** (`games/mb3d-demo`, `canal.rs`): the koi weaves just under the surface with a wake (`size` 0.3, strength 0.7) and spray off its bow ten times a second; every 4.2 s it leaps 0.7 m for 0.8 s, its wake off while it's in the air, splashing out (2.5 m/s) and back in (4.5 m/s) with two rings each; a fish rises somewhere ahead every 1.3 s (a weak slow ring); 44 cherry petals (one instanced draw, `NO_REFLECTION`) drift toward the camera on a 0.35 m/s current, are pushed aside by the koi and bob on the rings (`Ring::height`). The koi's motion is analytic in the canal's clock, so the wake and splashes are the same at 60 and 120 Hz.

**Cost**, `mb measure` (headless Chrome on an M-series Mac, the canal for 12 s, three runs each, GPU from paced steps): with all of this, GPU p50 3.3–3.6 ms; with the same build calling none of it (no wake, rings, splashes or petals), 2.7–3.4 ms, so roughly +0.3–0.5 ms, within the runs' noise of ±0.4 ms. CPU is unchanged at the timer's resolution (update 0.1, render 0.1, present 0.4 ms p95); the uniform grows by 2.2 KB (rewritten each frame, twice with the reflection). Per reflective pixel a ring costs ~25 ALU and one `cos`/`sin`/`exp`, a wake in reach ~150 ALU (the nearest-segment search) plus a few transcendental ops; on an A15 at a quarter of the M1's ALU, the canal's one wake and ≤ 6 rings over half the screen should stay under ~0.5 ms, to confirm on a device. Budget: a wake or two per scene, rings for events (not a constant drizzle of 16).

Not done: a simulated heightfield (a small wave grid around the camera that rings could bounce off walls in). It would need ping-pong render targets or a CPU grid uploaded every frame (WebGPU without compute or storage textures here), a fixed step for determinism, scrolling as the camera moves, and enough resolution for splash-sized waves (a 128² grid over 16 m is 12 cm a cell, coarser than a koi's ripples), for an effect the analytic terms already give in the cases games need. Also not done: waves on non-reflective materials, reflections of particles (splashes aren't mirrored), and wakes interacting with each other or the banks (they pass through walls).

### Organic meshes and skins built in code (added after the reflector)

A player called a code-built koi "very polygonal, barely looks like a fish at all". It was a squashed UV sphere and a cone, flat shaded, moved as one rigid piece: the SDK's builders were geometric primitives, and nothing could change a code-built mesh's shape over time, so fish couldn't undulate, tails couldn't sway and banners couldn't wave. The vignette is the **koi pond** in `games/mb3d-demo` (tap KOI; tap again for a close-up, the same fish stiff, and the old faceted koi).

**Shapes (SDK only, `gfx3d/organic.rs`).** Plain Rust on `MeshData`, tested natively:

- `Spline`: a centripetal Catmull-Rom curve through points, measured by arc length (`at(t)`, `tangent(t)`, `length()`).
- `MeshData::loft(&Loft, |t, u| section)`: a cross-section swept along a spline spine. The closure returns the section's point at `t` along the spine and `u` across the section, in the section's frame (x side, y up, z along the spine), so scale, twist, offsets and the shape itself can change per station. Frames are rotation-minimizing (double reflection), so curling tentacles don't twist. Closed sections make tubes (with optional flat caps; an end that shrinks to a point closes itself), open ones strips (fins, leaves, banners). `ends` bunches sections toward the ends where noses curve fastest. UVs are u across, v along.
- `smooth_normals(crease)`: angle-weighted normals shared by every vertex at the same position across edges flatter than `crease`, split across sharper ones; identical vertices are merged. UV seams and touching parts shade as one surface.
- `subdivide(levels, crease)`: Loop subdivision on the position-welded mesh (so UV seams don't crack), with creases: open borders, non-manifold edges and edges whose faces meet more sharply than `crease` follow the boundary rules (edge midpoints, 3/4–1/8 vertex rule, corners stay). UVs, colors and skin weights are interpolated per original vertex, so seams keep their attributes.
- `double_sided()`, and `MeshData::fish(&FishDesc) -> FishMesh { body, fins, eyes }`: a worked creature recipe from lofts (a rounded head, a tapering stalk that closes inside the tail, a forked tail fin, a long low dorsal, paired and anal fins with rays and edge-fading alpha in vertex colors, barbels), skinned to a chain along `FishDesc::spine()`. It's an example to copy for other creatures, not a creature library.

**Animating a code-built mesh: skins built in code.** Three mechanisms were possible: skins (bones and weights, the guest turning bones), morph targets built in code (weights per frame), or a host-side bend/wave deformer evaluated in the vertex shader. Skins won because mb3d 2 already had everything else:

- The GPU path (`vs_skinned`, the outline and shadow variants, the mirror pass) reads per-vertex joints and weights and a world-space palette of up to 64 joints, and `Scene` culls a skinned draw by a sphere around its joints. A code-built skin is the same data, so shadows, outlines, reflections, fog and the 128-skinned-draw cap apply unchanged.
- Bones are ordinary nodes, posed with `mb3d_node_transform`, which is already in the draw hash: determinism needs nothing new, and things parent to bones (a lantern on a tail) for free.
- It's general: a fish, a banner, a tassel, a tentacle and a koinobori are all chains with a traveling wave. Morph targets would cap motion at 4 blended shapes chosen in advance; a host deformer would be one more shader path, one fixed motion model, and new state to hash.

The ABI adds two things, both mb3d 2. **Mesh flag 4**: each packed vertex ends with `joints u16×4, weights unorm16×4` (renormalized to sum to exactly 1 the way glTF weights are; joint indices ≤ 63, else −2; an mb3d 1 game gets −2 for the flag, as before). **`mb3d_skin(node, ptr, count)`**: binds the node's skinned mesh to `count` (≤ 64, −4 past it) packed `Joint { node u32, inverse_bind f32×16 }` (68 bytes): a joint that isn't a live node is −1, a non-finite matrix −2, `count` 0 unbinds. Joints can be any nodes; the palette is `world(joint) × inverse_bind` and, as in glTF, the skinned node's own transform is ignored (make the bones its descendants and moving the node moves the mesh). A skin whose joints don't cover the mesh's joint indices, or no skin, draws the mesh rigidly in its rest pose. Binding (or setting the mesh of a skinned node) grows the mesh's per-joint culling reach from the inverse bind matrices. The call is folded into the draw hash (op 0x100 + 49, with its bytes).

**SDK** (`gfx3d/skin.rs`): `MeshData::joints`/`weights`, `with_joint(j)` (a rigid part on one bone) and `with_chain_weights(points)` (each vertex follows the bone it's nearest, blending into the next over half a bone either side of each joint); `Node::set_skin(&[(Node, Mat4)])` and `Skeleton` (`chain(parent, points)` or `new(parent, &[(parent_index, rest)])`, `bind(node)` (several meshes can share bones: a fish's body and its translucent fins), `turn(i, rot)`, `reset()`, and to hang things on bones `bone(i)`, `bones()`, `tip()`, `with_names`/`find(name)`, `rest_point(i)` and `socket(i, point)`, a node on bone `i` at a rest-pose point of the mesh); `Wave` (each bone turns about an axis by `amplitude × (head + (1 − head)·k) × sin(phase − 2π·waves·k)`, k = 0 at the first bone and 1 at the last, so the bend travels head to tail and grows toward it) and `Swim` (a wave whose beat is `idle + speed / (stride × length)`, stride 0.7 body lengths per beat as real fish, strength easing toward the speed, plus a bend into turns; dt-correct, so 60 and 120 Hz agree). `Mat4::inverse()` was added for inverse bind matrices.

**The koi pond, as built.** Five koi (`FishDesc` defaults, the big one with butterfly fins `fins: 2.4`), patterns in vertex colors from value noise (kohaku, sanke, tancho, yamabuki, showa), eyes merged into the body: one skinned body draw (PBR, roughness 0.28, rim 0.35) and one skinned fin draw (alpha, double-sided, a faint orange emissive) per fish over eight bones. Paired fins are weighted as if they reached back along the body, so they trail the wave instead of sticking out rigidly. Three koinobori (lofted open cloth tubes, scales in vertex colors) wave on two traveling waves plus a droop; the stone lantern's tassel swings on two. Rocks (jittered icosahedra, `subdivide(2, π)`, one instanced draw) and the lantern (boxes and a frustum, `subdivide(2, 0.9)` keeping its edges) are cages smoothed in code.

**Cost.** Measured with `mb measure games/mb3d-demo` (desktop headless Chrome, M-series Mac, 16 s live in the pond, tapping through every look): 22 draws, 52.6 k triangles, 14 skinned draws (10 for the koi, 3 streamers, the tassel), 16 shadow casters; `mb_update` 0.2 ms p95 (all the swims, waves and ~70 bone transforms, in wasm), `mb_render` 0.1 ms, presenting 0.4 ms p95, GPU 3.7 ms p50 / 4.5 ms p95 for the whole frame; `mb.verify()` matched over 1020 frames with five taps. Each skinned draw uploads a 4 KB palette and does 4 matrix fetches per vertex (a koi is ~1.5 k body and ~1.9 k fin vertices). Building is the expensive part: `MeshData::fish` takes ~1.9 ms natively (`cargo test -p maimbrain --release build_cost -- --ignored --nocapture`), and building and uploading the whole pond (five koi, three streamers, the rocks and lantern) took 35 ms in the one update that enters it, in wasm on the desktop; on an A15 that's perhaps 100 ms, under the 250 ms watchdog but a hitch, so build creatures in `init` or spread them over frames. A15 estimate: the CPU side scales with bones (~70 node transforms per frame here, microseconds), the GPU side like any 50 k-triangle scene, well inside the frame; to confirm on a device.

**Limits.** 64 joints per skin and 128 skinned draws per frame (shared with glTF); a skinned node can't also be instanced (its instance list wins and draws rigidly); skin weights are linear blend skinning (strong twists pinch, so keep per-bone turns modest, as `Swim` does); `subdivide` is Loop on triangles (quads aren't kept as quads) and shrinks a cage toward its center a little; `with_chain_weights` is distance-based, so for a mesh whose parts come near other bones (an arm by a torso) weight those parts with `with_joint` or by hand.

### Bones for generated models and flight (added after the music graph)

Players said a generated dragon "doesn't move at all" and a heron "doesn't feel alive"; the creator's notes: Tripo's avian rig came back with 65 joints and one wing, and serpentine clips coil the body. No ABI change: bones are glTF nodes the game already reaches with `node_find`.

**mb** (`crates/mb-cli/src/generate/spine.rs`): `mb model --spine` bakes the placed mesh, lays `spine_0…N−1` (head first) along the body's principal axis in the y–z plane at slice centroids, adds symmetric two-bone wings for birds (under a plain `wings` node, so the SDK finds their parent by name), writes Gaussian chain weights (≤ 4 per vertex) and inverse binds, and drops the old skin and clips. Also: leaf-joint merging for skins over 64 joints, a mirror check, the joint tree in the sidecar, a thicker-end facing check that turns a long creature that came back backwards, stable `<asset>/body` node names, and `--import` to run all of it on an existing `.glb`.

**SDK** (`gfx3d/skin.rs`, `gfx3d/creature.rs`): `Skeleton::adopt(root, &[(name, parent)])` takes a spawned model's own bones (rest transforms read from `Node::world` right after spawning, decomposed), `Skeleton::spine(root)` the `--spine` layout, `spine_len()` (Wave and Swim bend only the chain, not the wings). `Flight`: effort from climb, slowness and acceleration (eased), flapping vs gliding eased (never a snapped wing), beat rate eased (no bob discontinuity), coordinated-turn bank `atan(v·ω/g)` through a `Follow`, pitch from the climb, a downstroke bob, wing pose (a faster downstroke, the elbow lagging the shoulder by 0.9 rad, the hand folding on the upstroke), a level head (bone 0 undoes most of the bank and pitch, bone 1 turns the body back), a tail that lags pitch changes, `level_with` for birds sculpted standing. `Strike`: rear back, dive with wings swept back, flare, recover, as eased keys (`height`, `pitch`, `fold`, `reach`). `alive::{breath, anticipate, look_yaw, turn_toward}`.

Evidence: the creator's heron, dragon and koi (`games/mb3d-demo`, `--param scene=creatures`): `mb shot --smoothness --track-node` on the heron through two strikes is smooth at 60 and 120 Hz (peak 45 m/s², the strike's dive); the first version had a spike where the strike's 1.6× beat rate ended within a frame, fixed by easing the rate.

### Water v2 (`mb3d_water`, added after the organic meshes)

A player of a koi runner on the night canals (the reflector, ripples, wakes, splashes and sky v2 all in) said after four rounds that "the water still feels very inorganic and flat". It was: the reflector's water was a mirror bent by five procedural waves, with no flow, no small-scale detail, no depth, no foam where it met things and no sparkle. Water v2 is a look for that water: one call with a struct whose zeroed form is off, so a game that doesn't call it (or an mb3d 1 game) draws exactly as before. The vignettes are the canal (`canal.rs`: tap past the look without the beauty pass for a low view by the wall, then the same canal with water v1) and the koi pond (`koi.rs`), which had no water at all and now has a clear pond the koi swim in.

- **API.** `mb3d_water(Water)` (96 bytes, SPEC §5.4): `color`, `depth_fade`, `tint`, `scatter`, `foam_color`, `foam`, `flow`, `flow_speed`, `detail`, `detail_scale`, `sparkle`, `caustics`, `refraction`, `foam_width`. It applies to reflective materials while the reflector is on (it is the reflector's water); the last call wins. **The current can change every frame** (`flow`, `flow_speed`, and `detail_scale`, which sets how fast the ripples cross a meter): each layer's drift is kept from where it stood when they last changed, so the ripples carry on from where they are and only their direction and speed change. (Before, a layer's offset was `flow × speed × time` from the session's start, so turning the current a minute in jumped every ripple by a minute's worth of the difference: turning it smoothly made them race.) A look whose current never changes draws exactly as before. SDK: `gfx3d::water(&Water::canal().flowing(Vec3::Z, 0.35))`, `Water::lake()`, `Water::pond()`, and `Water::default()` to turn it off.
- **Ripples carried by a current.** A 256² RGBA8 tiling texture is made once on the CPU, the first time a game sets a look (`mb3d::water::water_noise`): r and g are the slope of 56 sine waves with whole numbers of cycles across the tile (so it tiles), 3–13 cycles in every direction, the longer a little steeper; b is tiling fBm (foam patches, glint twinkle); a is caustics (below). The shader samples the slope three times, at 1, 2.37 and 5.31 tiles per `detail_scale` meters. Each layer drifts downstream with the current at its own speed and a slightly turned angle, plus a slow crawl of its own, so still water isn't frozen and the pattern changes as it travels instead of sliding as one sheet. The drifts are worked out on the CPU from simulation time and wrapped to a tile, so they stay exact however long a session runs. Mipmapping averages a layer away as it gets finer than the pixel. The slope variance it loses goes into the GGX roughness instead (α² ≈ 2σ²), plus a small floor for ripples finer than the finest layer, so far water turns into a soft glitter path rather than shimmering, and a nearby light doesn't make single-pixel sparkles. Wake and crest foam is broken into patches by the foam noise, which is squeezed along the current so foam streams out in streaks.
- **The reflection.** The lookup moves to where the rippled surface sends the view ray: the reflected direction's change is projected onto the camera's axes (`screen_shift`), mirrored in y because the reflection image is. A tilt toward or away from the camera moves the reflection up and down much more than a sideways tilt moves it across, so lights on the water stretch into columns, as on real water. The two finer ripple layers count for 40% here (they still tilt the highlights fully), so reflections wobble and break at their edges but stay readable. The shift is scaled by the reflector's `distortion` and capped at 12% of the screen; the reflector's own swell (`ripple`) shifts it as much, so with a look on, a `ripple` of 0.1–0.2 is plenty (the canal uses 0.15); the reflection pass's scissor widens by that much. Where ripples are finer than the pixel, two more taps above and below smear the reflection vertically.
- **The water's body and what's under it.** What the water doesn't reflect (1 − the split-sum Fresnel) comes from its body: `color` lit by the sky's irradiance, the sun and the point lights as their light enters the water, and light scattered toward the camera (`tint` × `scatter`, strongest looking toward a light and on steep wave faces). The water under a lantern glows warm, and a low sun lights the waves from behind. With `depth_fade` > 0 the water is see-through:
  - **The under view.** Before the main pass (after the reflection), the host draws the camera's draws that reach below the plane (`Scene::collect_under`: not reflective materials, not 3D text, not what lies more than 6 × `depth_fade` below) into an HDR target at the reflection's resolution, scissored to the water. They draw with `fs_under`: the usual shading without fog (the water pixel is fogged over the whole path), dimmed by the water the light came down through, caustics included, discarding what's above the plane.
  - **Its alpha** is e^(−meters of water the view ray crosses before reaching that point), worked out exactly from the plane, so bilinear filtering blends transmittance across edges rather than distances. Blended draws leave it as it is (their alpha blend is zero/one), and it's cleared to 0 (nothing).
  - **Seeing through.** The water reads it at its pixel shifted by the broader ripples (`refraction`, more through deep water and less far away; the finest layer would scatter it into noise) and lets it through by `transmittance^(absorb / depth_fade)`, where the colors the water's own lacks are absorbed up to 1.8× faster (red first in green water). Fog applies to the water pixel as before.
  - **Shadows.** While the look is on, reflective materials don't cast sun shadows (otherwise the water would shade everything under it).
- **Foam where it meets things.** Where the under view says little water lies in front of something (`foam_width` meters along the ray), the water foams: a thin line right at the contact, and patches farther out shaped by the noise streaming with the current. Four taps around the pixel soften the edges of thin submerged parts. Only things that reach below the surface foam (walls, posts, rocks, a boat's hull, a fish's back): something resting exactly on the surface can't be told from something above it. Foam takes the look's `foam_color`, is lit like the water (the sun at any angle, a blurred level of the reflection), and covers the body and glints.
- **Glints.** For each light (the sun, with a one-tap shadow, and each point light) the water adds a Blinn-Phong lobe on the rippled normal. The lobe is energy-conserving and widened by the sub-pixel slope variance (exponent 2400 nearby, down to 16), times Fresnel, times a twinkle mask from the fine foam noise (averaged out where the glints merge into a glitter path), times `sparkle`. Past a luminance of 4 the water's brightness grows a quarter as fast, so bloom still picks the brightest glints without a low sun's path turning into a white blob.
- **Caustics.** The texture's alpha is light refracted through a smoother tiling field (14 waves of 2–5 cycles) onto a plane below. Photons from a 2× finer grid are moved by the slope where they cross, times a depth that puts the most curved 2% just past focus, and splatted bilinearly; the result is stored as (light − 0.8) / 2.6, mostly dark with bright webs. Two layers drifting apart are added, brightest where their webs cross.
  - **Under the water**, on non-reflective materials, the light comes from the sun (followed back to the surface along its direction) and the point lights, fading as e^(−depth / `depth_fade`).
  - **Above it**, on sides of things within 0.6 m of the water and facing it, the light is what the water throws back up (the pattern taken from the water in front of them, farther out the higher they are), so walls under lanterns ripple with warm light.
  - Every material shades with `fs_styled` while caustics are on.
- **Compatibility and determinism.** Without a water look nothing changes: the zeroed `Water` parses to off, the new uniform block (9 vec4s at the end of `Frame`) is zero, the two new frame bindings (12, the water texture; 13, the under view) are 1×1 black, and `fs_styled` takes the old path. Checked: mb3d-demo built on sdk-next (the main scene, the canal at four moments and under its dusk sky, the pond) gives the same pixels on the old and new host (at most 1 level, the frame-counter dither). `mb3d_water` is folded into the draw hash (op 0x100 + 50, with its bytes) like every other call, only when called. `mb.verify()` matches over 597 frames of the canal cycling its looks (water v2, by the wall, water v1, the dusk sky).

**Cost**, with `mb measure --ab` (headless Chrome on an M-series Mac; 12 alternating repeats of 25 redraws at 2, 4 and 7 s; ± is the 95% interval):
- **The canal** with water v2, against the same canal built on sdk-next (the reflector with its ripples and wakes, no look): +0.23 to +0.49 ms over three runs (the machine's noise; e.g. 3.59 → 4.08 ± 0.2 ms). The under view (20 draws: the walls, the boats, the koi) was too small to tell apart in one run and ~0.35 ms in another; caustics cost nothing measurable.
- **The koi pond** with water v2, against the same pond with a plain mirror: +0.87 ± 0.12 ms (2.98 → 3.85), about half of it (+0.46) the under view, which draws the bowl and the five skinned koi again. The reflector itself added ~0.5–0.7 ms to the pond, which had no water before.
- **CPU** is unchanged at the timer's resolution; the look's uniform is 144 bytes. Making the texture takes ~10 ms natively, once, the first time a game sets a look (256² × 56 waves, plus a 512² photon splat): a slightly long frame then.
- **On an A15**, at about a quarter of the M1's GPU throughput, figure ~1–2 ms for the canal's water and ~3.5 ms for the pond's, to confirm on a device. Cheaper: the reflector's `resolution` 0.35 (the reflection and the under view both shrink), `depth_fade` and `foam` 0 (no under view), `caustics` 0 (no per-pixel cost on other materials).

Not done:
- Foam trailing downstream of obstacles. One upstream sample of the under view drew a displaced copy of the contact outline rather than a trail; the streaming noise stands in.
- Contact foam for things that touch the surface without crossing it.
- Water v2 in the reflection pass: reflected walls don't show their caustics.
- Caustics on particles, and the water seen from below its surface.

### The beauty pass (`mb3d_grade`, `mb3d_shafts`, `mb3d_halos`, `mb3d_film`, added after the organic meshes)

After four rounds on the moonlit canal (fog, reflections, sky v2, water that reacts, a koi on bones) a player called it "nice", and said another layer of polish was missing before it would be gorgeous. mb3d had bloom, a vignette, chromatic aberration and ACES, but nothing that grades an image, and no light *in the air*: no beams from the moon through the mist, no glow hanging around a lantern in fog. The beauty pass adds four calls, each with a struct whose zeroed form is off (so every game that doesn't call them composites exactly as before), shown on the canal (tap to compare it with the same scene without it) and on Mistwood.

- **Grade** (`mb3d_grade(Grade)`, 96 bytes): color grading on the tonemapped image, in display values (sRGB 0–1), after `Post`'s contrast and before the vignette, the way a colorist works on a frame. In order: lift (`shadows`), gain (`highlights`) and gamma (`midtones`) per channel, `out = ((s + lift·(1 − s))·(1 + gain))^(2^−midtones)`; split toning, where a tint's hue minus its luma (×0.3, so tints never change brightness) is added with a weight that crosses from shadows to highlights around `0.5 − 0.3·balance` (smoothstep over ±0.3 of luma); `vibrance`, saturation that favors dull colors; then per channel an S-curve `contrast` (exponent `2^contrast` either side of 0.5, so it never clips) followed by the filmic `toe` and `shoulder`: cubic bumps `∓ k·0.5·t(1 − t)²` on each half that keep 0, 0.5 and 1 and the slope at 0.5, and stay monotonic for −1…1 (positive toe: inkier blacks; positive shoulder: a soft roll into white). Last, an optional 3D LUT: a texture that is an N²×N strip (N 2–64; blue slices left to right, red across a slice, green down), sampled with two bilinear taps blended across blue, mixed in by `lut_amount`. `amount` mixes the whole grade with the ungraded image (0 is off). `mb3d/beauty.rs` `Grade::apply` is the same math in plain Rust and is tested natively (a neutral grade is the identity; the curve keeps its fixed points and is monotonic; tints don't change luma). A neutral LUT on the GPU matches no LUT within one level of 255; the canal's hand-made LUT matches the same grade done on the CPU to within 0.9 levels on average. **LUTs from an editor**: `tools/lut.py` (copied into every new 3D game) writes the identity strip, stamps it into a screenshot as an 8 × 4 grid of slices (a 32³ strip is 1024 px wide, more than a phone screenshot), and cuts the grid back out of the graded screenshot as a strip; grade with color adjustments only. Presets: `Grade::moonlit()` (teal shadows, warm lantern highlights), `golden_hour()`, `neon()`, and `Grade::lerp` between two.
- **Light shafts** (`mb3d_shafts(LightShafts)`, 48 bytes): screen-space radial scattering (Mitchell, GPU Gems 3) from the sun or moon. A half-resolution pass makes the source: the scene's own brightness (`min(3·luma, 1)`) under a Gaussian glow of angular `size` around the light, where the sky shows, or where fog has all but hidden what's there (`fog_amount⁴`, so the far end of a misty canal shines but the midground doesn't). A quarter-resolution pass marches 32 steps from each pixel toward the light's screen position (up to `length` of the way), weighting nearer steps more (`decay` per step) and staggering the steps with interleaved gradient noise; the result is multiplied by how far the light faces the view (it fades out as the camera turns away; a light behind the camera gives none) and, by `fog`, by the fog in front of what the pixel shows (rays hang in the distance, not over things near the camera). The composite adds it, times `color × intensity` (zero color = the sun's hue), with bloom before exposure. Anything crossing the glow casts a dark ray, so they read when something with gaps stands in front of the light: the torii beams in front of the moon, tree trunks under a high moon. A light off screen still gives rays from the edge (its screen position is clamped to 1.5 screens away). Presets: `LightShafts::moonbeams()`, `sunbeams()`.
- **Halos** (`mb3d_halos(Halos)`, 32 bytes): the light each point light scatters toward the camera, integrated in closed form along every pixel's view ray up to what the pixel shows: for a ray passing a light at closest distance h (softened by the core `size`), `∫ dt / (h² + (t − tc)²) = (atan((T − tc)/h) + atan(tc/h)) / h` from the camera to the surface at distance T, times `σ·I / 4π` (σ the halo's `density`, or the fog's at the light's height, or 0.04 without fog), the light's extinction `e^(−σ·distance)` to the camera, and `e^(−h²/reach²)`, which stands in for mist's forward scattering (the pure integral falls off only as 1/h and washed the whole canal orange). So a halo grows with the fog, wraps around the lamp, spreads over what's behind it and is cut off by whatever is in front of it; bloom, a blur of bright pixels, does none of that. Every point light with intensity above 0 gets one (≤ 8), in its color × `tint`, at half resolution (from the nearest of each 2×2 block of the main pass's depth). Preset: `Halos::mist()`.
- **Film** (`mb3d_film(Film)`, 32 bytes): `grain`, value noise in cells of `grain_size` logical pixels (so it looks the same on any phone), new 24 times a second of *simulation* time (so it replays, pauses with the game and repeats in `mb shot`), strongest in the midtones, added last (after the vignette and the dither, so a game without grain keeps its exact pixels); and anamorphic `streaks`: a quarter-resolution pre-pass keeps what's brighter than `streak_threshold` (in scene units before exposure: lamps, glints, not lit surfaces), then two horizontal blurs of 17 taps (the second 6× as wide) stretch it over `streak_length` of the screen's width, added in `streak_color` (an anamorphic blue by default). Preset: `Film::subtle()`.
- **Passes.** Grading and grain are part of the composite (uniform branches; nothing runs while off). Shafts or halos keep the main pass's MSAA depth (stored and sampleable, as for depth of field) and run the half-resolution source pass; shafts add one quarter-resolution pass, streaks three. The targets are made the first time a game turns one on. Order per frame: … main → [depth of field] → [halos and the shafts' source → shafts → streaks] → bloom → composite (+ halos, shafts, streaks with bloom, then exposure, saturation, ACES, `Post` contrast, the grade and LUT, vignette, dither, grain). `mb.stats()` counts the passes.
- **Determinism.** The calls are folded into the draw hash like every other (ops 0x100 + 55 grade, + 56 shafts, + 57 halos, + 58 film, with their bytes); a LUT handle that isn't a live texture is stored as 0. Everything else is host-side drawing; the grain's seed comes from simulation time. `mb.verify()` matches on the canal over 14 s of tapping through every look and sky, and on Mistwood.
- **Compatibility.** Older bundles of mb3d-demo and Mistwood (built from the commit before this one) give the same pixels on the old and the new host within the frame counter's 1-level dither. The composite's uniform grew by 10 vec4s and its bind group by four textures (black stand-ins while off).
- **Tuning** (the skill's "Beauty pass"): lighting and sky first, then fog, then the grade, then shafts and halos, then bloom, then grain, each judged on `mb shot` sheets of mid-play, with restraint: the course, the player and the hazards stay the clearest things on screen. On the canal, the first try at moonbeams (a wide glow, fogged midground as a source) turned the whole frame into a cream haze, and an over-saturated highlight tint warmed the moon along with the lanterns; the presets are what was left after pulling both back.

**Cost.** `mb measure … --ab` against the same game built from the commit before (headless Chrome on an M-series Mac, GPU time of 25 redraws × 12 alternating repeats at 4 and 9 s, 95% CI), each effect alone and then together on the canal's night sky: the grade +0.07 ms (−0.12 … +0.26: too small to tell from noise), halos +0.12 ms (−0.12 … +0.36, likewise), shafts +0.41 ms (0.25 … 0.57), streaks and grain +0.32 ms (0.13 … 0.51, nearly all the streaks' three passes), **the whole pass +0.53 ms** (0.27 … 0.79) on a 3.9 ms frame; Mistwood's (grade, shafts, halos, grain; it already kept its depth for depth of field) +0.23 ms (0.02 … 0.44). The parts overlap (shafts and halos share the depth and the source pass). Runs of the same comparison differ by about ±0.2 ms. CPU is unchanged at the timer's resolution (update and render 0.1 ms, presenting 0.3–0.4 ms p95), and `mb.verify()` matched over 840 frames of the canal and 598 of Mistwood. An A15 has about a quarter of an M1 Pro's GPU throughput and a sixth of its bandwidth: roughly 2 ms for the canal's whole pass (1.6 ms of it shafts, 1.3 ms streaks; the grade and halos a few tenths each) and 1 ms for Mistwood's, inside the 16.7 ms frame with the rest of the canal (3–4 ms here); to confirm on a device. Cheaper: shafts only where a light is in view (`intensity` 0 otherwise turns the passes off), no streaks, halos alone (they share the source pass) cost little once depth of field already keeps the depth.

Not done: shafts from point lights (halos cover lanterns; a radial pass per light would multiply the shafts' cost); halos in the reflection (a reflected lantern glows through bloom only); halos around emissive surfaces without a light (give the lamp a point light, or let bloom carry it); volumetric (shadow-mapped) light in the fog; temporal accumulation (everything is per frame, so there's no ghosting but the quarter-resolution shafts keep a faint stipple from their jitter).

### Distance fade (`mb3d_node_fade`, `mb3d_draw_distance`, added after the beauty pass)

A player said of a scene with a town in the distance: "the background has a bunch of houses popping in and out almost randomly". Nothing in mb3d drew by distance: things appeared when the frustum, the camera's far plane or a game's own chunking let them in, at whatever distance that happened to be. Now a node can fade with distance instead, and a scene can set a default tied to its fog.

**Put cull distances inside the fog; fade, never pop.** Choose `end` at or inside the fog's far distance (where it's nearly solid), so things come out of the mist rather than appearing in clear air, and fade over a band (`start` well short of `end`: a quarter to a half of `end`), never a hard cutoff. `Fog::draw_distance()` gives such a band for a fog: from where it's 85% thick to where it's 98% (linear fog: its `end`).

- **API.** `node.set_fade(start, end)`, `node.clear_fade()` (inherit again), `node.never_fade()` (the player, a landmark: overrides the default and an ancestor's fade); `gfx3d::draw_distance(start, end)` / `clear_draw_distance()`; `Fog::draw_distance() -> Option<(f32, f32)>`. A fade applies to the node's descendants that don't set their own (`update_world` resolves it with the world matrix), so setting it on a spawned model's root fades the whole model. The draw distance applies only to nodes whose radius (one instance's, for an instanced node) is at most `DRAW_DISTANCE_MAX_SIZE` = ¼ of its end: ground, terrain and water planes keep drawing.
- **Culling** (`Scene::fade`, used by `collect_draws`, `collect_reflected` and `collect_casters`). A plain or skinned mesh fades as one by the distance `d` from the camera to its bounding sphere's center: visibility `v = clamp((end − d)/(end − start))`; at `v` = 0 it's culled (not drawn, not counted in triangles or draws, not cast, not reflected); at 1 it draws as if it had no fade (the normal pipeline, no dither). An instanced node is culled when its whole sphere is beyond `end`, and draws with no fade when its whole sphere is inside `start`; otherwise each instance fades in the shader by its own distance. Distances are from the real camera in every pass (reflections fade with what they reflect).
- **The dither.** `Draw::fade` = `[start, end, v]` reaches the shader in the per-draw `Object` uniform (grown from 128 to 160 bytes: `fade` at 128, the camera's position at 144; zeros mean no fade). `vs`/`vs_skinned` pass `v` on, `vs_instanced` works it out from the instance's world position; it's a flat varying. Opaque materials discard a pixel when `v` ≤ a threshold from interleaved gradient noise at the pixel (`fract(52.98·fract(0.0671·x + 0.0058·y))`): spatial only, so the pattern stands still from frame to frame (no crawling, nothing temporal to resolve), it breaks up into fine grain rather than a regular grid, and at 4× MSAA all of a pixel's samples go together. Blended materials scale their premultiplied color and alpha by `v` instead. Outlines dither with their draw.
- **Pipelines.** The discard lives in new fragment entry points (`fs_fade`, `fs_styled_fade`) used by five lazily built camera pipeline sets (mesh, mesh styled, skinned, skinned styled, instanced), only for draws currently inside their band, so opaque draws that aren't fading keep pipelines without `discard` (early depth and hidden-surface removal on tile GPUs). The reflection and under-water passes already discard, and apply the fade in `fs_mirror` and `fs_under`. Shadows aren't dithered: a fading node casts whole until it's culled (shadow distances are usually well inside draw distances).
- **Determinism and compatibility.** The calls are folded into the draw hash (ops 0x100 + 65 `mb3d_node_fade`, + 66 `mb3d_draw_distance`, with their floats). Both default off, so nothing changes for a game that doesn't call them: an `mb shot` of Mistwood before and after this change gives byte-identical PNGs.

Not done: dithered shadows (a shadow-pass fragment shader would cost every caster); a per-instance cull (an instanced node's far instances still run the vertex shader, then discard); fading 3D text, particles and trails by distance (fog covers them).

### The retro look (`mb3d_retro`, added after the distance fade)

A player wanted a mech duel to look like "Mode 7 style parallax backgrounds and SNES 16-bit pixel art meets Sega Saturn style 3D". mb3d drew everything at the phone's full resolution with 4× MSAA, trilinear textures, smooth fog and 8-bit color: the opposite of every part of that. The retro look is one call that brings the 32-bit console back, with the HUD left sharp.

- **API.** `gfx3d::retro(&Retro { resolution: (320.0, 240.0), color_bits: 5.0, dither: 0.6, vertex_snap: 1.0, fog_bands: 8.0, .. })`; presets `Retro::saturn()` (320×224, 15-bit, light dither, a little wobble, banded fog), `ps1()` (320×240, strong dither, more wobble), `arcade()` (384×224, no wobble), `snes()` (256×224, flat colors); `Retro::default()` is off.
- **Resolution.** The scene renders into a target whose pixels are square and a whole number of device pixels wide: `p = max(1, round(min(viewport) / min(w, h)))`, `size = round(viewport / p)`. On a portrait phone the short side (across) gets `min(w, h)` pixels and the long side as many as fit: `(320, 240)` on an iPhone 13 (1170×2532) is 234×506 pixels of 5×5 (a 4:3 budget turned into the phone's shape, not a letterboxed 4:3 picture). Whole-number pixels mean no uneven columns in the blow-up. The adaptive render scale is ignored while it's on (the scene is already a tenth of the pixels).
- **Blow-up.** The composite already runs once per device pixel; with the look on (its own entry point, `fs_composite_retro`, a copy of `fs_composite` with the retro steps: sharing one body with branches shifted a few pixels by one level in games without the look), each device pixel takes the center of its low-res pixel before anything else (`at = (floor(uv·size) + 0.5)/size`), so the scene, bloom, the shockwaves, the vignette and the grade are all constant across the block: an exact nearest-neighbour blow-up without a separate pass or sampler. mb2d draws afterwards into the full-resolution viewport, untouched: pixel-art HUDs and portraits stay crisp (draw their art pixels at whole multiples, SPEC §5.3).
- **Color.** After the grade and vignette (in display values, where the consoles quantized), each channel is cut to `2^bits − 1` levels with a 4×4 Bayer threshold taken from the low-res pixel's position, scaled by `dither` (0 is flat bands, the SNES look; 1 the full ordered pattern, the Saturn/PS1 look). The composite's usual 1-level noise dither is skipped while the look is on (it would break flat pixel colors); grain still applies if a game asks for it.
- **Vertex snap.** `vs`, `vs_instanced` and the outline shader end in `if frame.retro.x > 0 { clip = retro_snap(clip) }`: the NDC position rounded to a grid of `vertex_snap` low-res pixels (`frame.retro.x`; the reflection's copy of the frame has it off). Triangles jitter as they move, like the PS1 and Saturn's integer rasterizers. Particles, trails and 3D text don't snap, and neither do skinned meshes: in `vs_skinned` the branch alone changed how the compiler evaluated the skinned position, moving a few pixels of the koi pond by one level for games that never turn the look on (a separate skinned entry point for the look would fix it; not done).
- **Fog bands.** `fog_amount` rounds to `fog_bands` steps (`frame.retro.y`): fog arrives in flat bands as it did with the Saturn's table fog.
- **Hard edges.** The consoles had no antialiasing. The pipelines are all built for 4× MSAA, so rather than a second set without it, the look keeps the MSAA target (stored and sampleable instead of resolved by the hardware) and a small pass (`fs_resolve0`, post.wgsl's "retro resolve") copies each pixel's first sample into the scene target: edges stay a pixel hard, and it costs one read of a target a tenth the screen's size. Depth of field and the beauty pass read the depth as before.
- **Affine texture mapping** (the PS1's warping textures) is not done: it needs a `noperspective` varying, i.e. another set of pipelines.
- **Nearest textures** (`mb3d_texture_filter(kind, handle, mode)`; SDK `Texture::nearest()`, `Model::pixelated()`). Pixel-art textures under trilinear filtering turn to mush in the distance and to blur up close. A texture (kind 3), or every texture of a loaded glTF model (kind 6), can be sampled nearest instead: `shade_styled` reads the texel under the UV from the full-size image with `textureLoad` (repeating with `fract`), so no sampler or mip chain is involved and the frame bind group is unchanged. The material's uniform carries a mask of its nearest textures (`flags.z`); a material with any nearest texture draws with the v2 fragment shader (`styled`), and materials using a texture rebuild when its filter changes. No mipmaps means distant pixel-art floors shimmer as the camera moves, which is the period look; the retro look's low resolution keeps it in check. Op 0x100 + 77 (kind, handle, mode, result).
- **Parallax backdrops** (`mb3d_backdrop(ptr, count)`; SDK `gfx3d::backdrop(&[Layer])`). The SNES drew mountains and hills on background layers that scrolled at their own rates; mb3d had only a sky. Up to four `Layer`s (40 bytes: texture, flags, scroll factors, offset, `repeat_x`, `scale`, `y`, tint) are textures wrapped around a cylinder about the camera, drawn by one fullscreen pass right after the sky in the main pass (same depth test as the sky, so only where nothing opaque is; premultiplied over it), far layers first. A layer's column comes from the ray's yaw relative to the camera's plus the camera's yaw times the layer's `scroll.0` (1 fixed in the world like the sky, less turns slower and reads as farther, 0 sticks to the screen); its row from tan(elevation) less tan(pitch)·(1 − `scroll.1`), against the layer's bottom edge `y` and a height that keeps the texture's aspect (one repeat is 360°/`repeat_x` wide, rounded to whole repeats so it wraps). The camera's yaw is unwrapped on the host frame to frame, so a slow layer doesn't jump when the yaw crosses ±π. Texels are read nearest from the full-size image (`textureLoad`), so pixel art stays square. Not done: the backdrop isn't seen in reflections, and it isn't drawn at full resolution under the retro look (it's part of the scene). Op 0x100 + 76 (count, bytes, result). Chosen over an mb2d "under" layer because it has to sit behind the 3D but in front of the sky, follow the 3D camera, and go through the same fog, grade and retro pixels as the rest of the scene.
- **Mode 7 floor** (SDK only: `MeshData::mode7_floor(radius, tile, segments)`, `gfx3d::mode7_anchor(camera, tile, y)`). The SNES's Mode 7 was one big tiled image under a per-line affine transform: a ground plane in perspective. In mb3d that is an ordinary mesh: a square `2 × radius` across, cut into `segments²` quads (vertices for fog, lighting and the vertex snap to act on), with UVs equal to the position over `tile` meters, so a tiling texture repeats once per tile in world units. Drawn with a nearest texture and an unlit material it reads as Mode 7; `mode7_anchor` puts its node under the camera snapped to whole tiles every frame, so it never runs out and its pattern never slides; turning or sliding the node rotates and scrolls the ground. The horizon: linear fog whose color is the backdrop's lowest color fades the floor's far edge into the backdrop's bottom (`games/mb3d-demo` fogs to the near hills' darkest green). No new ABI. Like the SNES, texels shimmer in the distance (no mipmaps); the retro look's resolution and fog bands keep it in check.
- **Determinism and compatibility.** `mb3d_retro` is folded into the draw hash (op 0x100 + 75, with its bytes). `Frame` grew one vec4 (`retro`, at the end) and the composite's uniform one vec4; both are zero unless a game turns the look on. Checked: `mb shot` of mb3d-demo's main scene, canal and koi pond (2 s and 5 s) and Mistwood (3 s) on the host before this change and after the whole retro set (look, nearest textures, backdrop) gives byte-identical PNGs. The retro scene itself (`--param scene=retro`) replays: `mb.verify()` matched over 480 frames.
- **When the retro look hurts** (added after Bolt Brawl, whose owner found its mechs "really hard to see"). The look suits low-poly, flat-colored models built for it, big on screen, in a lit scene. It hurts small subjects (at a 240–448 pixel budget a mech covering 3% of the screen is a few dozen pixels), dark scenes (a few color levels and banded fog crush the darks: with 6-bit color, mb3d-demo's muddy dragon has a frame L* of 1–5) and textured generated models (the texture is the detail; low resolution and few levels erase it). Toon bands do the same to a texture. What to keep instead: full resolution with crisp edges (a thin dark outline, a rim, smooth shading: `MaterialStyle::hero()`), a lit scene (`Lighting::hero()`), and the period flavor in the HUD and backdrops rather than on the subject. `mb shot --readability` warns when the subject doesn't separate, and when the look is on (`mb.stats().retro`) it says the look may be the cause.
- **Cost.** `mb measure games/mb3d-demo --param scene=retro --ab-param retro=off,on` (headless Chrome, M-series Mac, 3 sessions): full resolution 2.35 ms GPU, Saturn look 1.78 ms, **−0.58 ms (−25%)**, 95% CI −0.72 … −0.43: the look is cheaper than what it replaces (a tenth of the pixels; the composite's extra steps and the first-sample copy are a few ALU and one small read). `--quick` on the scene: 1.47 ms GPU, 3+1 draws, 3.6 k triangles; CPU unchanged (update and render 0.1 ms p95).

### Lighting a textured hero (`Lighting::hero`, SDK only, added after the retro look)

Bolt Brawl's owner couldn't see the mechs: generated, textured models in dark backlit arenas, three toon bands with rim and outline, the retro look at 640×448 with 6-bit color, and textures cut to 256². What mb3d gives a textured PBR model was checked first:

- **Sky fill: yes.** Smooth materials get image-based light from the sky: nine SH irradiance coefficients (a fill from every direction, brighter from the bright side of the sky) and a GGX-prefiltered cube for reflections (`ibl.rs`). Sky v2's atmosphere and a painted sky (`sky_texture`) are baked into both, so `Atmosphere::day()` lights a model blue-white from above and the ground color from below. Toon materials get the same fill, flat, and half the reflection.
- **Metal: yes.** Metallic surfaces show the sky's prefiltered reflection (split-sum with the BRDF table), so under a day sky metal reads as bright, sky-colored highlights; under a near-black sky it's black (the "Readable metals" recipe).
- **Rim with smooth shading: yes.** `MaterialStyle::rim` adds `rim × smoothstep(0.55, 0.8, 1 − N·V) × (0.3 sun + 0.5 base)` whatever `toon_bands` is.
- **Missing: the combination.** Nothing pointed a builder to "bright sky, key light from the camera's side, smooth shading, rim" as one setup, and the defaults (`Sky::default()` is a near-black space sky, the sun's default direction is fixed in the world) give a dark fill and, for a camera that turns, a backlit subject.

So no new op: `gfx3d::Lighting { sun, atmosphere, post }` with `Lighting::hero()` (a day atmosphere; a warm key at intensity 3.4 from high over the shoulder of a camera looking down −z, shadows; exposure 1, bloom 0.2 over 1.6, vignette 0.08), `.key_from(forward)` to turn the key with another camera, and `gfx3d::lighting(&l)` setting all three; and `MaterialStyle::hero()` (no toon bands, rim 0.45, a 1 px dark outline). `games/mb3d-demo --param scene=hero` lights the generated dragon (512² textures) that way, and `--param look=muddy` lights the same model like Bolt Brawl. `mb shot --readability`: hero outline ΔL* 35 with 97% of it at 15+, frame L* 46–78; muddy ΔL* 3, 15%, frame L* 1–5. Both replay (`mb measure … --seconds 4`: `mb.verify()` matched over 240 frames each); the draw hash of other scenes doesn't change (no renderer change).

A camera-relative fill light (a second, shadowless directional light) would help a hero that must stay backlit; it's not done, because the sky fill and a key from the camera's side covered the cases here.

### Sharp textures at a slant (16× anisotropic filtering, `Post::sharpen`, added after `Lighting::hero`)

Bolt Brawl's builder found no anisotropic filtering or sharpen option, and the mechs' textures looked soft at an angle. Textures were already mipmapped (`create_texture` builds the full chain with a box-filter pass) and sampled trilinear with `anisotropy_clamp: 4`, so a surface seen at a slant fell to a mip four times too blurry along its short axis past 4:1. The fix:

- **16× anisotropy by default** on the repeat sampler every material texture goes through (`mb3d repeat` in `gpu3d/mod.rs`; WebGPU's `maxAnisotropy`, which needs linear min, mag and mipmap filters, as it has). Nearest textures (`Texture::nearest`) read texels with `textureLoad` and are unaffected; the clamp sampler (sky, IBL, reflections) stays isotropic. WebGPU takes any `maxAnisotropy` and clamps it to what the hardware does: 16 on Apple GPUs in Chrome (Dawn → Metal) and in WebKit's WebGPU on iOS, which passes it to `MTLSamplerDescriptor.maxAnisotropy` (1–16). No device limit or feature to request; the runtime and the iOS app needed no change.
- **`Post::sharpen`** (0–1, the old reserved last float of `Post`, so a game built before it sends 0, off): in the composite (`fs_composite`, `sharpen_gain`), an unsharp mask on lightness against the 4 neighbours, in a tone-compressed space (x/(1+x)) so highlights don't ring, held to a quarter of the local range past the neighbourhood's min and max so edges don't halo; the pixel's color is scaled, keeping hue. Off, it's one uniform branch and the image is unchanged. Not with the retro look (its composite is separate and its pixels are hard already), and off in `mb.isolate`'s plain redraw.

Measured on `games/mb3d-demo --param scene=hero --param view=grazing` (a low camera along a 2 m-tiled steel deck, `assets/deck_plate.jpg`, the dragon side-on), shots at 3 s, luma of 720×1280 shots: in the far deck (rows 690–790, seen at a few degrees), edge energy (mean gradient) +27% and high-pass RMS +7.5% at 16× over 4×, the tread pattern resolving where it was a smear; the mid deck +3.5%; the dragon's flank (magnified, not at a slant) unchanged. `sharpen=0.4` adds +34%/+28% edge energy over 16× in the far deck and +21% on the dragon. Cost (`mb measure --final`, the desktop preview's GPU, an Apple GPU): 4× 2.60 ± 0.07 ms, 16× 2.85 ± 0.48 ms in separate runs, within what separate browser sessions differ by (the same scene measured 3.05 ± 0.34 in another run); `--ab-param sharpen=0,0.4` −0.02 ms (95% CI −0.38 … +0.33). Extra anisotropic taps are only taken where a texture's footprint is stretched, and they hit the same cache lines as the trilinear ones; the mobile cost is texture bandwidth on floors and walls seen edge-on, small next to the scene's shading.

### Rigs posed in code: masks, layers, IK, gaits (added after Bolt Brawl's boss mechs)

Bolt Brawl's boss mechs (generated meshes rigged by Tripo into 41-joint biped skeletons) were animated in a prototype by code: key poses per attack beat, two-joint leg IK with planted feet, a stomping gait, springs for strike stops, hit recoil and landing squash, all a pure function of fight time so replays match. It read as a heavy mech at phone size and cost nothing measurable (CPU 0.1 ms p95, GPU within noise). Everything it needed by hand is now in the kit.

- **Masks and additive layers** (ops 0x100 + 87, 88, 89). Before, a clip sample overrode a bone the game set by hand (the samples resolve when the frame draws), so a clip and code couldn't share a bone in one frame, and a clip played on every bone it has channels for.
  - `mb3d_anim_mask(node, clip, time, weight, ptr, count)` is `mb3d_anim` for only the listed nodes (`count` × (node u32, weight f32), ≤ 256), each at `weight` × its own weight; the clip's other channels are skipped. The blend is unchanged (weights short of 1 are made up by the rest pose), so a 0.4 mask weight is a 40 % clip.
  - `mb3d_anim_take(node, out)` resolves the node's samples so far, writes its local transform (10 floats) and drops them, so a `mb3d_node_transform` after it wins. It returns 1 if the node had samples, 0 if not (its transform as it is: a read of a node's local transform), −1.
  - `mb3d_node_get_parent(node)`: the parent's handle (0 at the root). A loaded model's hierarchy wasn't visible to the game, which a humanoid map and limb masks need.
  - All three are in the draw hash (op, arguments, mask bytes, results and the floats written).
  - **SDK** (`gfx3d/anim.rs`): `Mask` (`with(bone, w)`, `set`, `weight`, `scaled(k)`, `Mask::below(model, root, bone, w)` for a whole limb by walking every named node's parents, `Skeleton::mask(&[i], w)`, `Skeleton::mask_below(i, w)`); `Node::pose_masked(clip, t, w, &mask)`, `Animator::apply_masked(node, &mask)` (several animators on one model, each on its own bones); `Node::take_pose()` (Some(clip pose) and the game owns the bone this frame), `Node::local()`, `Node::parent()`; `Skeleton::add_turn(i, rot)` (a procedural turn on top of this frame's clip pose, or the rest pose if no clip moved the bone, so it never accumulates frame to frame) and `Skeleton::add_clip(model, clip, t, w, mask)` (a clip on top of a procedural pose: each bone's sample less its rest, `additive(base, rest, sample)` = base · rest⁻¹ · sample and base.pos + sample.pos − rest.pos, over what the game set). Cost: one host call per bone per layer (41 bones: ~80 calls a frame).
- **Rigs by what their bones are** (SDK only, `gfx3d/rig.rs`, `gfx3d/skin.rs`). `Skeleton` didn't know Tripo's bone names, and `turn` works in the bone's own frame, which on a generated rig points anywhere (Tripo's `L_Thigh` rest rotation is (0.96, −0.13, 0.05, 0.25)), so hand-keyed poses were unusable.
  - `classify(name)` reads a bone name: a part (`Hips`, `Spine`, `Chest`, `Neck`, `Head`, `Shoulder`, `UpperArm`, `Forearm`, `Hand`, `Thigh`, `Shin`, `Foot`, `Toe`) and a side from a prefix (`L_`, `Left`, `Bip01 L `), a suffix (`.L`, `_r`) or a word inside (`LeftUpLeg`), after namespaces (`mixamorig:`, `Armature|`) and `DEF-`; twist, roll, end, IK and finger bones are left out (limbs only: Tripo's neck bones are `NeckTwist01/02`). `humanoid_map(&[(name, parent)])` picks one bone per semantic name in `HUMANOID` (`hips`, `spine`, `chest`, `neck`, `head`, `shoulder_l`, `upper_arm_l`, `forearm_l`, `hand_l`, `thigh_l`, `shin_l`, `foot_l`, `toe_l` and `_r`): the one nearest the root where several match (Tripo's `Hip` over `Pelvis`, Mixamo's `Spine` as `spine`), the farthest spine bone as `chest`; Blender's metarig numbered spine (`spine` … `spine.006`) is mapped by number. Tested on Tripo's 41-joint biped, Mixamo, the Blender metarig, Unity-style and 3ds Max Biped names.
  - `Humanoid::find(model, root)` reads the spawned model's node names and parents (`Node::parent`), maps them and adopts the bones (`Skeleton::adopt_nodes`, each under its real parent, named semantically); `index`, `node`, `turn(name, rot)`, `rest_point`, `left_x()` (which side the rig's `_l` bones are on: generated rigs differ), `rig_names`.
  - `Skeleton::turn_model(i, rot)`: the turn in the model's frame, relative to the parent: the local rotation becomes rest · W⁻¹ · rot · W, W being the bone's rest rotation in the model's frame (`rest_rot(i)`, from its inverse bind matrix). With the parents at rest the bone ends up at rot · W; turns down a chain compose (each bone's accumulated model-frame turn is its parents' times its own). `orient(i, rot)` is absolute instead (world rotation root · rot · W, whatever the parents are doing); `set_world_rot(i, q)`, `world(i)` (posed, from `Node::world`), `ground_rot()` (the root's heading only) and `heading(q)`. The skeleton now keeps its root and each bone's real parent node.
- **IK** (SDK only, `gfx3d/ik.rs`). `two_bone(a, b, c, target, pole)` is the analytic two-joint solve (law of cosines for the hip angle, the knee placed in the plane of the reach and the pole direction's part across it, else the chain's own bend): the upper bone's turn maps its direction *and* its bend plane onto the new ones (so a knee's hinge axis stays the knee's own axis: no sideways knees), the lower bone's turn is a hinge in that plane; a target out of reach is reached for straight, and it returns the reach (0–1). `TwoBoneIk { upper, lower, end, flat }` (`leg(&rig, 'l')`, `arm`) applies it in world space on the pose the bones have now (`Skeleton::world`, `set_world_rot`, re-reading the lower bone after the upper turned so twist bones between are carried), and `flat` puts the foot at its rest orientation under the root's heading (`ground_rot() · rest_rot(foot)`), flat whatever the knee and body do. `LookAt { bone, forward, yaw_limit, pitch_limit, speed }`: `aim(forward, dir)` gives the yaw (about the model's up) and pitch to a direction in the model's frame; `update(dt, &sk, Some(target))` moves toward it, clamped to the limits, by at most `speed·dt` (so 60 and 120 Hz agree), back to straight ahead with None; `apply` orients the bone absolutely in the model's frame (it keeps looking whatever the chest does).
- **Keyed poses and kicks** (SDK only, `motion.rs`). `PoseKeys<T: Lerp>` (`new(v).to(at, v, ease).hold(s).trembling(amount)…`): keys on any clock (seconds since an attack, or a tell's progress 0–1), eased into each key by its `Ease`, held, with `sample(t)` the first key's value before and the last's after; `tremble(t, hz)` is a ±1 shake (0.7 sin(2π·hz·t) + 0.3 sin(2π·1.618·hz·t + 1.3)) times the key's amount, growing over the last fifth of the move into the key and through its hold, the "now" tell. `Lerp` now covers `Vec3` and `Quat` (slerp), and any pose struct of them. `kick(t, hz, damping)` is a spring's response to a unit kick `t` s after it, in closed form, normalized to peak at 1: critically damped (ζ ≥ 1) `ω t e^(1−ωt)`, underdamped `e^(−ζωt) sin(ω_d t) / peak`, so it's a function of the time since the kick, not of the `dt`s (`Spring::kick` integrates); `Kick { at, amount, hz, damping }.value(t)` keeps the moment, not a state.
- **A mech's walk** (SDK only, `gfx3d/gait.rs`). `MechGait::new(rest_feet)` (or `from_rig(&rig, body)`: the feet where they stand, in the moved node's frame): `stride` (m per cycle, 1.6), `lift` (0.5), `duty` (0.6 of the cycle each foot is planted: both feet down 20 % of the time, heavy), `dip` (0.18 m) and `dip_hz`, `roll` (0.07 rad), `settle_hz`, `min_speed`; `scaled(k)`. `update(dt, pos, yaw, vel)` advances the phase by the distance walked (`speed·dt / stride`); a foot lifts when its phase (the second half a cycle behind) crosses `duty` and lands when it wraps, each crossing found within the frame and the body's position and yaw interpolated to that instant, so landing spots don't depend on the frame rate (60 vs 120 Hz: same stomps within 2 cm). A foot lands at its home (the rest spot under the body at that instant) plus a lead of `duty·stride/2` along the velocity (so it's under the hip mid-stance), which makes sideways and backward steps and turns fall out; in the air it moves on smoothstep with a lift of `lift·sin(π s^0.8)` (up fast, down hard). Stopping: below `min_speed` the phase runs at `settle_hz` only while a foot is in the air or a planted foot is more than 0.12 strides from home, then stops with both feet down. Each landing is a `Stomp { foot, pos, strength }` (0.35 + 0.65 × the step's length over a full step); `body_offset()` is the dip, `dip·strength·kick(since_stomp, dip_hz, 1)` (critically damped from the landing's exact time), `body_tilt()` the hip roll toward the planted foot's side (eased), `apply(&rig, &legs, forward)` the IK. Tested: steps forward, sideways and backward alternate and keep up, replays are identical, and a stop settles both feet under the body.
- **Parts on bones** (SDK only, `gfx3d/skin.rs`). `Node::attach_to(bone)` reparents a node to a bone keeping it where it is: its local transform becomes `decompose(bone_world⁻¹ · its_world)` (`attach_offset`), so a part placed by hand with the model at rest (a FITS/SOCKETS table's shield, blade or claw) stays put on the arm as the arm moves; `attach_at(bone, &world_transform)` places it and attaches in one; `Humanoid::attach(part, "forearm_l")`. The bone's world includes the rig's own scale (a Tripo armature is in centimeters under a 0.01 node), which the offset undoes, so the part keeps its size.
- **The example** (`games/mb3d-demo`, `--param scene=mech`, `mech.rs`): Bolt Brawl's HAULER (`assets/mech_hauler_rig.glb`, 1.39 MB with its six Tripo clips, from the prototype) through a 10 s beat sheet, all a function of scene time: a sideways strafe and back on `MechGait` (dust from each `Stomp`, a camera shake from `kick`), a keyed strike (`PoseKeys`: windup held with a tremble, a quad-in punch with a 1.3 m lunge, a `Kick` stop, the follow-through, recovery), a hit at 7 s (a reel pose, a recoil `Kick` on the chest and body, pushed back 1.1 m so the gait steps backward), `Humanoid::find` on Tripo's names, poses keyed in the mech's frame (+z front; the model's facing found from heels to toes) through `turn_model`, its `Idle` clip added at 30 % on the upper body (`add_clip`), the head on the camera (`LookAt`), and a briefcase fitted in the right hand at rest and attached (`Humanoid::attach`). `mb measure games/mb3d-demo --param scene=mech --seconds 12` (headless Chrome, M-series): 717 frames, CPU update 0.20 / render 0.10 ms p95, GPU 2.75 ± 0.22 ms, 4 draws, 7.0 k triangles, **verify match (717 frames)**.
